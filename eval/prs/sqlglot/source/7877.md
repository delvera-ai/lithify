# PR #7877: fix(oracle): preserve UNPIVOT IN-list literal labels [CLAUDE]

https://github.com/tobymao/sqlglot/pull/7877

## PR body

## Problem

In Oracle `UNPIVOT`, the `AS <constant>` label in the `IN` list is a string/numeric **literal** (the value placed into the `FOR` column), not an identifier. The Oracle generator corrupts it on output:

```python
>>> import sqlglot
>>> sqlglot.transpile("SELECT * FROM sales UNPIVOT(q FOR p IN (q1 AS 'Prod1'))", read="oracle", write="oracle")[0]
"SELECT * FROM sales UNPIVOT(q FOR p IN (q1 AS Prod1))"      # 'Prod1' -> bare identifier (semantic change)
>>> sqlglot.transpile("SELECT * FROM sales UNPIVOT(q FOR p IN (q1 AS 1))", read="oracle", write="oracle")[0]
'SELECT * FROM sales UNPIVOT(q FOR p IN (q1 AS "1"))'        # 1 -> quoted identifier "1" (invalid Oracle SQL)
```

The AST parses correctly — this is a generation bug. The string label silently changes meaning, and the numeric label becomes `"1"`, which Oracle rejects (it requires a constant there).

## Cause

`Generator.UNPIVOT_ALIASES_ARE_IDENTIFIERS` defaults to `True`, so `pivotalias_sql` rewrites each literal label into an identifier. The Oracle generator never overrides it, even though Oracle's UNPIVOT labels are literals — the same situation BigQuery already handles (`generators/bigquery.py` sets it to `False`).

## Fix

Set `UNPIVOT_ALIASES_ARE_IDENTIFIERS = False` on `OracleGenerator`, matching BigQuery. Expression labels (e.g. `col AS 'PREFIX ' || CHR(38) || ' SUFFIX'`) are unaffected, since the identifier/literal rewrite branches don't fire for a concatenation.

## Testing

Added two round-trip identities to `tests/dialects/test_oracle.py` (string labels and numeric labels). `pytest tests/dialects/test_oracle.py` → 25 passed / 215 subtests; `ruff check` clean. The existing expression-label UNPIVOT test is unchanged.
