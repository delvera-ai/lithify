# PR #8300: fix(transforms): keep the table when dropping an unnamed UNIQUE constraint [CLAUDE]

https://github.com/tobymao/sqlglot/pull/8300

## PR body

Fixes #8297.

`remove_unique_constraints` pops the parent of every `UniqueColumnConstraint`. That is right for the two wrapped spellings (`a INT UNIQUE` sits in a `ColumnConstraint`, `CONSTRAINT c UNIQUE (a)` in a `Constraint`), but an unnamed table-level `UNIQUE (a)` sits directly in `Schema.expressions`, so its parent is the `Schema` that is `Create.this` and the whole table disappears:

```python
>>> sqlglot.transpile("CREATE TABLE t (a INT, b STRING, UNIQUE (a))", read="duckdb", write="spark")
['CREATE TABLE']
```

After:

```python
>>> sqlglot.transpile("CREATE TABLE t (a INT, b STRING, UNIQUE (a))", read="duckdb", write="spark")
['CREATE TABLE t (a INT, b STRING)']
```

The fix pops the wrapper only when the parent is a `ColumnConstraint` or `Constraint`, and pops the constraint itself otherwise. This affects the four generators that apply the transform (hive, spark, spark2, materialize; databricks inherits from spark). `PRIMARY KEY` and `FOREIGN KEY` in the same position are untouched.

Tests: `test_remove_unique_constraints` in `tests/test_transforms.py` covers the three spellings, multiple constraints, coexistence with PK/FK, and the MySQL `UNIQUE KEY` / `UNIQUE INDEX` parse path; a `validate_all` in `tests/dialects/test_spark.py` pins the output for databricks, hive, materialize, spark and spark2 (duckdb keeps the constraint). The table-level cases fail before the fix and pass after. Full suite: OK.

Disclosure: implemented with Claude. I reviewed each line and reproduced the behavior locally.


## Issue #8297: Table level UNIQUE constraint drops the entire CREATE TABLE on Spark, Databricks, Hive and Materialize

**Fully reproducible code snippet**

A table level `UNIQUE` constraint without any constraint name makes the whole `CREATE TABLE` go away when you generate for Spark, Databricks, Hive, Spark2 or Materialize. Only the words `CREATE TABLE` are left. And there is no warning also.

```python
from sqlglot import parse_one

sql = "CREATE TABLE t (a INT, b STRING, UNIQUE (a))"

for d in ["databricks", "spark", "spark2", "hive", "materialize", "snowflake", "duckdb"]:
    print(d, "->", repr(parse_one(sql, read="duckdb").sql(dialect=d)))
```

Output on main (`30.17.1.dev96`):

```
databricks -> 'CREATE TABLE'
spark -> 'CREATE TABLE'
spark2 -> 'CREATE TABLE'
hive -> 'CREATE TABLE'
materialize -> 'CREATE TABLE'
snowflake -> 'CREATE TABLE t (a INT, b VARCHAR, UNIQUE (a))'
duckdb -> 'CREATE TABLE t (a INT, b TEXT, UNIQUE (a))'
```

What I expected is that the constraint gets dropped and the rest of the table stays. That is what the other two spellings of the same constraint are already doing:

```
CREATE TABLE t (a INT UNIQUE)                     -> 'CREATE TABLE t (a INT)'
CREATE TABLE t (a INT, CONSTRAINT c UNIQUE (a))   -> 'CREATE TABLE t (a INT)'
CREATE TABLE t (a INT, UNIQUE (a))                -> 'CREATE TABLE'
```

`PRIMARY KEY (a)` and `FOREIGN KEY (a) REFERENCES u(b)` in the same place are both fine. So it is the unnamed table level `UNIQUE` only.

**Notes**

`remove_unique_constraints` in `sqlglot/transforms.py` is popping the parent of the constraint and not the constraint itself:

```python
for constraint in expression.find_all(exp.UniqueColumnConstraint):
    if constraint.parent:
        constraint.parent.pop()
```

But the parent is not the same node in all three spellings:

| input | `constraint.parent` |
| --- | --- |
| `a INT UNIQUE` | `ColumnConstraint` |
| `CONSTRAINT c UNIQUE (a)` | `Constraint` |
| `UNIQUE (a)` | `Schema` |

For the first two the parent is a wrapper around the constraint, so popping the same is correct. For the third one the `UniqueColumnConstraint` is sitting directly inside `Schema.expressions`, so the parent is the `Schema` itself, which is `Create.this`. Popping that takes away the table name and all the columns, and then the generator has nothing left to print.

The transform is used by `generators/spark.py`, `generators/spark2.py`, `generators/hive.py` and `generators/materialize.py`. Databricks is getting it from Spark.

Dropping the constraint is fine, these engines do not enforce `UNIQUE` anyway. The problem is dropping the table. And it is silent, so a DDL script which you transpile will just fail at the engine with a syntax error and nothing points back to the constraint.

I hit this while round tripping the statements in `tests/fixtures/identity.sql` through different write dialects and checking the output is stable.

**Official Documentation**

- Databricks [CREATE TABLE constraints](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-ddl-create-table-constraint), which is the reason the constraint has to be dropped in the first place
- The unnamed table level form is standard SQL and Postgres, DuckDB and Snowflake all accept it. So it does come up when existing DDL is being converted over to Spark or Databricks.
