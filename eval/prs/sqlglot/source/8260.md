# PR #8260: fix(dialect): fall back on TokenError when an operand isn't a JSON path

https://github.com/tobymao/sqlglot/pull/8260

## PR body

A `->` / `->>` operand that is a plain string literal rather than a JSON path (e.g. a key containing an apostrophe) raises `TokenError` from the JSON path tokenizer. `TokenError` is a sibling of `ParseError` under `SqlglotError`, so it escaped the `to_json_path` fallback and aborted the whole parse instead of leaving the literal operand in place — even for duckdb/sqlite, which relax `STRICT_JSON_PATH_SYNTAX` precisely for this.

```python
sqlglot.parse_one("SELECT a -> 'it''s' FROM t", read="duckdb")  # TokenError on main
```

Widen the except to cover both. Fixes #8249.


## Issue #8249: DuckDB/SQLite: a JSON key containing an apostrophe raises TokenError, losing the statement

- Read dialect: `duckdb`, `sqlite`
- Write dialect: n/a — the failure is on input, before any generation
- Still reproduces on `main` at `a60171e8`

A JSON key containing an apostrophe raises `TokenError` during parsing, so the whole statement is lost. The input is valid SQL in both dialects and the apostrophe is escaped correctly.

```
input:    SELECT a -> 'it''s' FROM t     -- valid DuckDB and SQLite; the key is: it's
raised:   sqlglot.errors.TokenError: Error tokenizing 'it''
expected: parses, with the key preserved
```

**Fully reproducible code snippet**

```python
import sqlglot

sqlglot.parse_one("SELECT a -> 'it''s' FROM t", read="duckdb")
```

```
sqlglot.errors.TokenError: Error tokenizing 'it''
```

Same for `read="sqlite"`.

The SQL tokenizer handles the literal correctly anywhere else, which isolates it to the JSON path re-read:

```python
import sqlglot

print(sqlglot.parse_one("SELECT 'it''s' FROM t", read="duckdb").sql(dialect="duckdb"))
# SELECT 'it''s' FROM t
```

It fails only where the literal is the operand of `->` / `->>`.

**Where it comes from**

`Dialect.to_json_path` (`sqlglot/dialects/dialect.py:1171`) already has a fallback for an operand that is not a JSON path — warn, and return the literal unchanged:

```python
            try:
                return parse_json_path(path_text, self)
            except ParseError as e:
                if self.STRICT_JSON_PATH_SYNTAX and not path_text.lstrip().startswith(
                    ("lax", "strict")
                ):
                    logger.warning(f"Invalid JSON path syntax. {str(e)}")

        return path
```

`JSONPathTokenizer` raises `TokenError`, which derives from `SqlglotError` directly rather than from `ParseError`, so it escapes this handler and aborts the parse instead of falling back.

DuckDB shows the intent most clearly: it sets `STRICT_JSON_PATH_SYNTAX = False` (`sqlglot/dialects/duckdb.py:25`) to relax exactly this kind of operand, and still fails, because the exception escapes before the flag is consulted.

The tokenizer raises because it maps `'` to `QUOTE` with `STRING_ESCAPES = ["\\"]` (`sqlglot/jsonpath.py:14`), and `path.name` has already been unescaped by the SQL tokenizer — so `'it''s'` arrives as `it's` and the apostrophe opens a string that is never closed.

Widening the except clause makes both dialects parse, and the operand stays a plain literal so it round-trips with the escaping intact:

```diff
-            except ParseError as e:
+            except (ParseError, TokenError) as e:
```

```
unpatched   duckdb   TokenError          patched   SELECT a -> 'it''s' FROM t
            sqlite   TokenError                    SELECT a -> 'it''s' FROM t
```

**Related**

#3185 was the same fallback failing on a `ParseError` it did catch (a `-` in a key), and was fixed. This is the sibling exception class that still escapes it. The apostrophe issues fixed so far — #4090, #8108, #8114 — are all about the generated path literal rather than the parser.

**Official Documentation**

- DuckDB [JSON functions](https://duckdb.org/docs/stable/data/json/json_functions) — `->` takes a JSON path.
- SQLite [path arguments](https://sqlite.org/json1.html#path_arguments) and [string literals](https://sqlite.org/lang_expr.html#literal_values_constants_) — `''` escapes a literal apostrophe, and a path key may hold arbitrary characters.
