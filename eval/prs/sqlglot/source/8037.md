# PR #8037: fix(bigquery)!: treat a bare WEEK date part as WEEK(SUNDAY) in truncation functions

https://github.com/tobymao/sqlglot/pull/8037

## PR body

BigQuery [docs](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/date_functions#date_trunc): "Weeks begin on Sundays. WEEK is equivalent to WEEK(SUNDAY)". The parser already normalized bare WEEK in DATE_DIFF and LAST_DAY, but not in the truncation functions, so the two spellings of the same expression transpiled differently:

```sql
-- 2008-11-10 is a Monday, BigQuery returns 2008-11-09 for both spellings
DATE_TRUNC(DATE '2008-11-10', WEEK(SUNDAY))
-- duckdb before and after: CAST(DATE_TRUNC('WEEK', ... + INTERVAL '1' DAY) + INTERVAL '-1' DAY AS DATE), returns 2008-11-09

DATE_TRUNC(DATE '2008-11-10', WEEK)
-- duckdb before: DATE_TRUNC('WEEK', ...), returns 2008-11-10, silently wrong
-- duckdb after: same output as the WEEK(SUNDAY) spelling
```

The parser now normalizes bare WEEK to WEEK(SUNDAY) in DATE_TRUNC, TIMESTAMP_TRUNC and DATETIME_TRUNC. The simplifier resolves these units through the dialect's week offset, folding when the start day matches and leaving the expression untouched when it doesn't; without this, the existing bare WEEK simplification fixtures regress.

Also reworked the week tests so that degraded outputs assert UnsupportedError instead of pinning SQL whose semantics differ from the source.

Breaking because bare WEEK truncation output changes for every Monday-start target dialect. All new test queries were verified against live BigQuery and DuckDB.

close #8011

## Issue #8011: bigquery -> duckdb: LAST_DAY(x, WEEK(<day>)) drops the week unit and returns the last day of the month

Two related BigQuery week-semantics problems on the `bigquery` -> `duckdb` path, plus one one-liner at the end. Read dialect `bigquery`, write dialect `duckdb`. All of it still reproduces on `main` at `f4ebda71` (30.14.1.dev41), Python 3.13, DuckDB 1.5.5.

The two asks are separate: the first is a straightforward broken guard, the second I do not think I should send a patch for without you steering it — see the ripple measurement.

## 1. `LAST_DAY(x, WEEK(<day>))` silently drops the week unit

`_last_day_sql` already has an unsupported-date-part guard, but the `WeekStart` node routes around it, so `WEEK(<day>)` falls into the `MONTH` default and emits a plain `LAST_DAY(...)` with no warning at all:

| bigquery input | duckdb output | `self.unsupported` fires? |
|---|---|---|
| `LAST_DAY(d, ISOWEEK)` | `LAST_DAY(d, ISOWEEK)` | yes — `Unsupported date part 'ISOWEEK' in LAST_DAY function` |
| `LAST_DAY(d, WEEK(SUNDAY))` | `LAST_DAY(d)` | no |
| `LAST_DAY(d, WEEK(MONDAY))` | `LAST_DAY(d)` | no |

Against the two worked examples on Google's `LAST_DAY` page:

```py
import sqlglot, duckdb

for sql in ("SELECT LAST_DAY(DATE '2008-11-10', WEEK(SUNDAY))",
            "SELECT LAST_DAY(DATE '2008-11-10', WEEK(MONDAY))"):
    out = sqlglot.transpile(sql, read="bigquery", write="duckdb")[0]
    print(out, "->", duckdb.sql(out).fetchone()[0])

# SELECT LAST_DAY(CAST('2008-11-10' AS DATE)) -> 2008-11-30
# SELECT LAST_DAY(CAST('2008-11-10' AS DATE)) -> 2008-11-30
```

| input | BigQuery docs | duckdb 1.5.5 via sqlglot |
|---|---|---|
| `LAST_DAY(DATE '2008-11-10', WEEK(SUNDAY))` | `2008-11-15` | `2008-11-30` |
| `LAST_DAY(DATE '2008-11-10', WEEK(MONDAY))` | `2008-11-16` | `2008-11-30` |

Cause: `sqlglot/generators/duckdb.py:163` reads the unit as `expression.text("unit")`. That gives `'WEEK'` for a `Var` and `'ISOWEEK'` for the unsupported case, but `''` for the `WeekStart` node that `WEEK(SUNDAY)` parses into — so the `if not unit or unit.upper() == "MONTH"` on line 165 wins and the `self.unsupported(...)` on line 206 is unreachable for these units. `_last_day_sql` came in for Snowflake in #6614, which has no `WEEK(<weekday>)` spelling, so the node never came up.

Fastest way to see it: `tests/dialects/test_bigquery.py:3564-3567` already contains exactly this ZetaSQL example as a bigquery -> bigquery identity. Adding a `write={"duckdb": ...}` to it exposes the bug in about fifteen seconds. There is no test anywhere that writes a bigquery `LAST_DAY` with any WEEK unit to duckdb — coverage is zero.

## 2. bare `WEEK` and `WEEK(SUNDAY)` in `DATE_TRUNC` transpile to different dates

Google's date-granularity definitions say, verbatim: "**Weeks begin on Sundays. `WEEK` is equivalent to `WEEK(SUNDAY)`**". sqlglot already agrees with that on the write side — `Generator.weekstart_sql` (`generator.py:6218-6222`) collapses `WEEK(SUNDAY)` back to bare `WEEK` for BigQuery, with the comment "BigQuery specific optimization since `WEEK(SUNDAY) == WEEK`", and the `week_trunc` table in `test_week` asserts that round-trip. It does not agree on the read side, so the two spellings of one BigQuery expression produce two different DuckDB answers:

```
SELECT DATE_TRUNC(DATE '2008-11-10', WEEK)
  -> SELECT DATE_TRUNC('WEEK', CAST('2008-11-10' AS DATE))
  =  2008-11-10 00:00:00

SELECT DATE_TRUNC(DATE '2008-11-10', WEEK(SUNDAY))
  -> SELECT CAST(DATE_TRUNC('WEEK', CAST('2008-11-10' AS DATE) + INTERVAL '1' DAY) + INTERVAL '-1' DAY AS DATE)
  =  2008-11-09
```

(2008-11-10 is a Monday. The second form also comes back as a `DATE` and the first as a `TIMESTAMP`.)

No test feeds a bare `WEEK` into a bigquery `DATE_TRUNC` anywhere in the suite, which is why the asymmetry with the `week_trunc` table has stayed invisible.

### Why I am not sending a patch for this one

The obvious fix is to have the BigQuery parser normalise a bare `WEEK` date part to `WeekStart(SUNDAY)`. I simulated that by transpiling `DATE_TRUNC(d, WEEK(SUNDAY))` where `DATE_TRUNC(d, WEEK)` is written today, across 14 write dialects. It fixes duckdb and changes 12 others for the worse, because everything downstream flows through `Generator.weekstart_sql` (`generator.py:6218`), whose fallback is `self.func("WEEK", ...)`:

| write dialect | today | after that change |
|---|---|---|
| duckdb | `DATE_TRUNC('WEEK', d)` | `CAST(DATE_TRUNC('WEEK', d + INTERVAL '1' DAY) + INTERVAL '-1' DAY AS DATE)` |
| snowflake, postgres, presto, trino, redshift, tsql, athena, hive | `DATE_TRUNC('WEEK', d)` | `DATE_TRUNC(WEEK(SUNDAY), d)` |
| spark, databricks | `TRUNC(d, 'WEEK')` | `TRUNC(d, WEEK(SUNDAY))` |
| clickhouse | `dateTrunc('WEEK', d)` | `dateTrunc(WEEK(SUNDAY), d)` |
| mysql | `STR_TO_DATE(CONCAT(YEAR(d), ' ', WEEK(d, 1), ' 1'), '%Y %u %w')` | `DATE(d)`, with `Unexpected interval unit:` logged |

That is 13 of 14 outputs changed, and the BigQuery-only `WEEK(<weekday>)` date-part spelling leaking into dialects that have no such syntax. MySQL is the worst of it: the truncation disappears entirely.

So this is not a one-liner in the parser, and I would rather not guess at the shape. Do you want the read-side normalisation plus a `weekstart_sql` fallback that lowers `WEEK(SUNDAY)` to whatever each dialect's plain week unit is, or is it better handled entirely inside the BigQuery/DuckDB pair? Happy to implement whichever you point at.

### Open question, not a claim

`LAST_DAY(x, WEEK)` with a bare unit currently gives `2008-11-16` for `2008-11-10`. If bare `WEEK` really is `WEEK(SUNDAY)` everywhere, that should be `2008-11-15`. But the `LAST_DAY` page lists bare `WEEK` only as "Equivalent to 7 `DAY`s", with no start day and no worked example, so I am not asserting it — flagging it as part of the same question. Note `tests/dialects/test_snowflake.py:2813-2819` pins the Snowflake reading of bare `WEEK` and looks correct as-is, so whatever changes here should not be shared with that path.

## 3. Small one: `DATE_TRUNC(x, ISOWEEK)` emits SQL DuckDB rejects

```
SELECT DATE_TRUNC(DATE '2008-11-10', ISOWEEK)
  -> SELECT DATE_TRUNC('ISOWEEK', CAST('2008-11-10' AS DATE))
  =  Conversion Error: extract specifier "ISOWEEK" not recognized
```

No warning is emitted. Mentioning it because it sits in the same code path and `LAST_DAY` already has the `self.unsupported` call for `ISOWEEK`; if you would rather this stay lenient, ignore this section.

## What is and is not verified here

The DuckDB results above are real: DuckDB 1.5.5 in-process, and every number in this issue came out of a run just now. **I have not run anything against BigQuery.** The expected values are either Google's own published worked examples (`2008-11-15`, `2008-11-16`) or their stated date-part definition plus calendar arithmetic. If any of them is wrong, the first item still stands on its own — the `ISOWEEK`/`WEEK(SUNDAY)` asymmetry in the table is internal to sqlglot.

Official documentation:
- [`LAST_DAY`](https://cloud.google.com/bigquery/docs/reference/standard-sql/date_functions#last_day) — supported date parts and the two `WEEK(SUNDAY)` / `WEEK(MONDAY)` examples
- [`DATE_TRUNC`](https://cloud.google.com/bigquery/docs/reference/standard-sql/date_functions#date_trunc) — "Weeks begin on Sundays. `WEEK` is equivalent to `WEEK(SUNDAY)`", and the `ISOWEEK` definition

I have a fix ready for item 1 with a regression test, and can open a PR whenever you want it. Item 2 I would want direction on first. If you consider any of this working as intended — leniency on 3, or the bare-`WEEK` reading in 2 — say so and I will drop it.
