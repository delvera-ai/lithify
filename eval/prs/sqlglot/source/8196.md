# PR #8196: Feat(bigquery): support digit-prefixed field names

https://github.com/tobymao/sqlglot/pull/8196

## PR body

closes #8175

## Issue #8175: BigQuery: data.144A_FLAG silently mis-parses to data.144 AS A_FLAG; compiled build raises bare TypeError

BigQuery allows JSON/STRUCT field names that begin with digits. `sqlglot` mis-tokenizes the leading digits as a numeric literal, which produces a structurally invalid `Column` node. The two distribution builds then diverge: the pure-Python wheel returns the bad AST silently, while `sqlglot[c]` raises a bare `TypeError` that is not a `SqlglotError`.

Both behaviours reproduce on 30.17.0.

## Reproduction

```python
import sqlglot
sqlglot.parse_one("SELECT data.144A_FLAG FROM t", dialect="bigquery")
```

| input (dialect=`bigquery`) | `sqlglot` 30.17.0 | `sqlglot[c]` 30.17.0 |
|---|---|---|
| `SELECT data.144A_FLAG FROM t` | parses, wrong AST | `TypeError` |
| `SELECT t.1a FROM t` | parses, wrong AST | `TypeError` |
| `SELECT STRING(data.144A_FLAG) FROM t` | `ParseError` | `TypeError` |

## 1. Silent mis-parse (pure-Python build)

The field access is reinterpreted as a float projection plus an implicit alias:

```python
>>> p = sqlglot.parse_one("SELECT data.144A_FLAG FROM t", dialect="bigquery")
>>> p.sql(dialect="bigquery")
'SELECT data.144 AS A_FLAG FROM t'

>>> repr(p.expressions[0])
Alias(
  this=Column(
    this=Literal(this=144, is_string=False),
    table=Identifier(this=data, quoted=False)),
  alias=Identifier(this=A_FLAG, quoted=False))
```

`Column.this` is a `Literal`, so `Column.parts` returns `['Identifier', 'Literal']` — but it is annotated `-> list[Identifier | Star]` (`sqlglot/expressions/core.py:1730`). The round-tripped SQL is not equivalent to the input, and nothing signals that.

## 2. Bare `TypeError` on the compiled build

`sqlglot[c]` type-checks arguments at runtime, so the same invalid node raises before the parser's own error handling can turn it into a `ParseError`:

```
  File "sqlglot/parser.py", line 6791, in _parse_atom
  File "sqlglot/parsers/bigquery.py", line 524, in _parse_column
TypeError: union[sqlglot.expressions.core.Identifier, sqlglot.expressions.core.Star] object expected; got sqlglot.expressions.core.Literal
```

`sqlglot/parsers/bigquery.py:524` is `parts = column.parts`.

This is the part with the wider blast radius: `except SqlglotError` is the documented way to handle untrusted SQL, and it does not catch this. Installing the `[c]` extra therefore changes the exception contract — code that is correct against the pure wheel crashes against the compiled one, on identical input and an identical version. We hit this in production: a single unparseable view aborted an entire warehouse metadata crawl for a month, because our handler caught `SqlglotError`.

## The input is valid BigQuery

Confirmed with a BigQuery dry run (`Valid: True`):

```sql
WITH t AS (SELECT JSON '{"144A_FLAG":"Y"}' AS data)
SELECT STRING(data.144A_FLAG) AS is_144a FROM t
```

Digit-leading keys are common in financial reference data (`144A_FLAG` is the Rule 144A marker in Bloomberg feeds), and BigQuery emits such expressions unquoted in the `view_definition` it stores in `INFORMATION_SCHEMA.VIEWS` — so they arrive in tooling whether or not the author quoted them.

## Suggested direction

1. In the BigQuery dialect, treat `<identifier> . <digit-leading token>` as field access rather than a numeric literal, so the example parses to a `Column`/`Dot` over `144A_FLAG`.
2. Independently of (1): whatever the parser cannot model should surface as a `ParseError`, not a `TypeError`. Since the compiled build's runtime checks can fire before the parser's own validation, it would help to guarantee that `parse_one` only ever raises `SqlglotError` — otherwise every caller of `sqlglot[c]` needs a bare `except Exception`.

## Environment

- sqlglot 30.17.0 (also reproduces on 30.11.0), both `sqlglot` and `sqlglot[c]`
- Python 3.13, macOS (arm64)
- dialect: `bigquery`
