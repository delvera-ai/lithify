## Issue #8345: SQLite nanosecond date differences are ten times too small

Transpiling a one-day nanosecond difference from T-SQL to SQLite returns `8640000000000` instead of `86400000000000`.

Reproduced on `main` at `5cfb5997a`, Python 3.13.15 and SQLite 3.53.1:

```python
import sqlite3
import sqlglot

query = "SELECT DATEDIFF_BIG(NANOSECOND, '2024-01-01', '2024-01-02')"
generated = sqlglot.transpile(
    query, read="tsql", write="sqlite", unsupported_level=sqlglot.ErrorLevel.RAISE
)[0]
with sqlite3.connect(":memory:") as connection:
    actual = connection.execute(generated).fetchone()[0]

expected = 24 * 60 * 60 * 10**9
print(generated)
print("actual:", actual)
print("expected:", expected)
```

Output:

```text
SELECT CAST((JULIANDAY('2024-01-02') - JULIANDAY('2024-01-01')) * 8640000000000.0 AS INTEGER)
actual: 8640000000000
expected: 86400000000000
```

[SQLite's `JULIANDAY` difference is in days](https://www.sqlite.org/lang_datefunc.html), so the nanosecond multiplier is `86400 * 10**9`. The `NANOSECOND` branch of `SQLiteGenerator.datediff_sql` is missing one zero. The [T-SQL input uses documented `DATEDIFF_BIG` syntax](https://learn.microsoft.com/en-us/sql/t-sql/functions/datediff-big-transact-sql).

This reports the conversion factor only, not nanosecond precision in SQLite's floating-point date arithmetic. The exact one-day example avoids that precision question.

Disclosure: investigated with GitHub Copilot; the generated SQL was executed locally on SQLite. No SQL Server engine was run.
