# PR #8267: fix(sqlite): preserve explicit end bound in RANGE CURRENT ROW window frames [CLAUDE]

https://github.com/tobymao/sqlglot/pull/8267

## PR body

## Root cause

`SQLiteGenerator.windowspec_sql` (`sqlglot/generators/sqlite.py`) collapses any `RANGE` frame starting at `CURRENT ROW` down to the short form `RANGE CURRENT ROW`, without checking whether the frame has an explicit end bound. `RANGE BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING` therefore transpiles to `RANGE CURRENT ROW`, which is a different frame: it changes an aggregate's result set, not just its formatting.

The original fix (`9b529b744`, "Fix(sqlite): support `RANGE CURRENT ROW` in window spec") only intended to cover the no-end-bound case; its own regression test is `RANGE CURRENT ROW` with nothing else. The guard never checks `expression.text("end")` before returning the short form.

## Fix

Add `and not expression.text("end")` to the guard, so the short form is only emitted when no end bound was specified. When an end bound is present (even an explicit `CURRENT ROW`), the frame now renders through the normal `windowspec_sql` path unchanged.

## Verification

- `sqlglot.transpile("SELECT RANK() OVER (RANGE BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING) FROM tbl", read="sqlite", write="sqlite")` returns the collapsed, wrong output on `main` (confirmed on HEAD `bac1a897b`) and the unmodified input on this branch, same Docker image both sides.
- Confirmed the semantic difference against real `sqlite3`: `RANGE CURRENT ROW` and `RANGE BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING` produce different `SUM(...) OVER (...)` results on the same data.
- Added two `validate_identity` cases to `tests/dialects/test_sqlite.py` (explicit `UNBOUNDED FOLLOWING` end, and explicit `CURRENT ROW` end); both fail on `main` and pass on this branch. Full `tests/dialects` suite (716 tests) passes on Python 3.9 and 3.14, the two ends of the CI matrix.

## Issue #8209: SQLite: RANGE window frames starting at CURRENT ROW silently lose their end bound

**Fully reproducible code snippet**

The SQLite generator collapses any `RANGE` frame that starts at `CURRENT ROW` to the short form `RANGE CURRENT ROW`, even when the frame has an explicit end bound ([`windowspec_sql`](https://github.com/tobymao/sqlglot/blob/a5804178a558acc3a04eacb0057c280c52963ecd/sqlglot/generators/sqlite.py#L372-L379) checks `kind` and `start` but not `end`). In SQLite an omitted end bound defaults to `CURRENT ROW`, so the frame silently collapses to the current row's peer group and results change, with no warning:

```python
import sqlite3, sqlglot

sql = "SELECT id, SUM(amt) OVER (ORDER BY id RANGE BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING) AS remaining FROM t"
out = sqlglot.transpile(sql, read="sqlite", write="sqlite")[0]
print(out)  # SELECT id, SUM(amt) OVER (ORDER BY id RANGE CURRENT ROW) AS remaining FROM t

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE t (id INTEGER, amt INTEGER)")
con.executemany("INSERT INTO t VALUES (?, ?)", [(1, 10), (2, 20), (3, 30)])
print(con.execute(sql).fetchall())  # [(1, 60), (2, 50), (3, 30)]
print(con.execute(out).fetchall())  # [(1, 10), (2, 20), (3, 30)]  <- silently different
```

`RANGE BETWEEN CURRENT ROW AND 1 FOLLOWING` is truncated the same way, and every read dialect is affected when `write="sqlite"` (duckdb/postgres/snowflake all produce `RANGE CURRENT ROW` here). `ROWS` frames and `RANGE` frames with other start bounds are generated correctly. Verified on main (a580417) with SQLite 3.53.

The parser captures the full frame (`end='UNBOUNDED'`, `end_side='FOLLOWING'`), so the expected output is to keep the `BETWEEN` form whenever `end` is set — SQLite has supported it since 3.28 — and only use the short form for frames that genuinely end at the current row.

**Official Documentation**

https://www.sqlite.org/windowfunctions.html#frame_specifications — a frame specification with no ending boundary defaults to ending at the current row.
