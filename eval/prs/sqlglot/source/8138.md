# PR #8138: fix(executor): only truncate typed division when both operands are integers [CLAUDE]

https://github.com/tobymao/sqlglot/pull/8138

## PR body

Fixes #8132.

## The bug

The Python executor registers `exp.Div` in `PythonGenerator.TRANSFORMS`, which bypasses `Generator.div_sql` and its operand-type guard. `_div_sql` then applies `int()` to every division carrying `typed=True`, regardless of operand types:

```python
from sqlglot.executor import execute

schema = {"t": {"n": "INT"}}
tables = {"t": [{"n": 10}]}

for dialect in ("postgres", "sqlite", "mysql", "duckdb", None):
    r = execute("SELECT n / 3.0 AS x FROM t", schema=schema, tables=tables, dialect=dialect)
    print(f"{str(dialect):9} -> {[tuple(row) for row in r.rows]}")
```

```
postgres  -> [(3,)]        # expected [(3.3333333333333335,)]
sqlite    -> [(3,)]        # expected [(3.3333333333333335,)]
mysql     -> [(3.3333333333333335,)]
duckdb    -> [(3.3333333333333335,)]
None      -> [(3.3333333333333335,)]
```

It fails silently -- a plausible wrong number, no exception. Casting does not help, because the truncation happens after annotation: `SELECT n::double / 3` returned `3` too.

## The fix

`typed=True` records that the source dialect divides *integers* as integers, not that it truncates everything. Postgres' `10 / 3` is `3`, but `10 / 3.0` is not -- and neither is `10 / 3::numeric`.

So `int()` is applied only when neither operand is a `REAL_TYPES` member, which is the same guard `Generator.div_sql` already applies for this flag. Note `REAL_TYPES` covers `DECIMAL`/`NUMERIC`/`MONEY` as well as the floats, which is what makes it the right predicate here rather than "is it floating point".

Operands whose type is unknown are still truncated, so behaviour with no schema is unchanged -- including the existing `1 / 2 typed=True -> 0` case in `test_execute_callable`.

## Tests

`test_typed_division` covers both `TYPED_DIVISION` dialects across: a float literal on either side, an explicit cast, a decimal column, integer/integer (must stay `3`), negative truncation (must stay `-3`), and the unknown-type fallback.

Full suite passes: `SKIP_INTEGRATION=1 python -m unittest` -> 1314 tests, OK.


## Issue #8132: Python executor truncates all division to int for TYPED_DIVISION dialects (postgres, sqlite), ignoring operand types

**Before you file an issue**

- Read dialect: `postgres`
- Executed with: `sqlglot.executor.execute(..., dialect="postgres")`
- Still exists on main: yes — `_div_sql` in [`sqlglot/generators/python.py#L61-L72`](https://github.com/tobymao/sqlglot/blob/main/sqlglot/generators/python.py#L61-L72) is unchanged. Tested on 30.13.0.

**Summary**

In the Python executor, any division parsed from a `TYPED_DIVISION` dialect (`postgres`, `sqlite`) is truncated to an integer regardless of operand types, so `n / 3.0` returns `3` instead of `3.3333...`. It fails silently — a plausible wrong number, no exception.

**Fully reproducible code snippet**

```python
from sqlglot.executor import execute

schema = {"t": {"n": "INT"}}
tables = {"t": [{"n": 10}]}

for dialect in ("postgres", "sqlite", "mysql", "duckdb", None):
    r = execute("SELECT n / 3.0 AS x FROM t", schema=schema, tables=tables, dialect=dialect)
    print(f"{str(dialect):9} -> {[tuple(row) for row in r.rows]}")
```

```
postgres  -> [(3,)]        # expected [(3.3333333333333335,)]
sqlite    -> [(3,)]        # expected [(3.3333333333333335,)]
mysql     -> [(3.3333333333333335,)]
duckdb    -> [(3.3333333333333335,)]
None      -> [(3.3333333333333335,)]
```

An explicit cast does not help — `SELECT n::float / 3 FROM t` also returns `3`, as does `SELECT n * 1.0 / 3 FROM t`.

Two literals work, because `simplify` constant-folds them before codegen and no `Div` node survives: `SELECT 10 / 3.0 FROM t` correctly returns `3.3333333333333335`. The bug needs one non-literal operand.

**Cause**

`Postgres.TYPED_DIVISION = True`, so the parser sets `typed=True` on the `Div`. The Python executor registers `exp.Div` in `PythonGenerator.TRANSFORMS`, which bypasses `Generator.div_sql` and its operand-type guard:

```python
# sqlglot/generator.py — div_sql, the guard that is bypassed
elif not self.dialect.TYPED_DIVISION and expression.args.get("typed"):
    if l.is_type(*exp.DataType.INTEGER_TYPES) and r.is_type(*exp.DataType.INTEGER_TYPES):
        return self.sql(exp.cast(l / r, to=exp.DType.BIGINT))
```

```python
# sqlglot/generators/python.py — _div_sql, unconditional
if e.args.get("typed"):
    sql = f"int({sql})"
```

Types are annotated correctly by the time codegen runs, so the guard would work if it were consulted:

```python
import sqlglot
from sqlglot import exp
from sqlglot.executor.python import Python
from sqlglot.optimizer import optimize

o = optimize(sqlglot.parse_one("SELECT n / 3.0 FROM t", dialect="postgres"),
             schema={"t": {"n": "INT"}}, dialect="postgres")
d = next(o.find_all(exp.Div))
print(d.left.type, d.right.type, d.right.is_type(*exp.DataType.INTEGER_TYPES))
# INT DOUBLE False
print(Python().generate(o))
# SELECT int(DIV(scope["t"]["n"], 3.0)) FROM "t" AS "t"
```

Applying the same `INTEGER_TYPES` check in `_div_sql` looks like it would fix this while preserving genuine `int / int` truncation. Happy to open a PR if that's the direction you'd want.

**Official Documentation**

- [Mathematical Functions and Operators](https://www.postgresql.org/docs/current/functions-math.html) — `numeric / numeric → numeric`, `double precision / double precision → double precision`; only `integer / integer` truncates.
- [Operator Type Resolution](https://www.postgresql.org/docs/current/typeconv-oper.html) — `integer / numeric` resolves to `numeric`, not `integer`.
