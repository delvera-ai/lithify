# PR #8284: fix(postgres): preserve quoting of the one-byte "char" type [CLAUDE]

https://github.com/tobymao/sqlglot/pull/8284

## PR body

Fixes #8280

PostgreSQL's "char" is a one-byte type that is distinct from CHAR/bpchar, and
quoting is the only way to name it. sqlglot was dropping the quotes and emitting
CAST(x AS CHAR), which answers the same cast with a different value.

Resolving quoted type names is deliberate and tested (1::"int" -> CAST(1 AS INT)),
so I did not change that. Instead I added an opt-in Parser attribute,
QUOTED_TYPES_TO_PRESERVE, that lists type names whose meaning changes when quoted;
Postgres sets it to {"char"}. Matching is case sensitive, since "CHAR" is not the
one-byte type. Such a type is parsed into a USERDEFINED DataType holding the quoted
identifier, which is the same representation already used for 1::"udt".

The check is gated on SUPPORTS_USER_DEFINED_TYPES so Redshift, which inherits the
Postgres parser but has no one-byte "char", keeps its current behaviour.

Tests added in tests/dialects/test_postgres.py cover the cast, the :: form, the
array form, and that "CHAR" still resolves to CHAR.

Disclaimer: I used an LLM while writing this patch. I have reviewed and understand
every line of it and I am happy to answer questions about it.

## Issue #8280: Postgres: CAST(x AS "char") is parsed as CHAR, so the one-byte "char" type becomes bpchar

- Read dialect: `postgres`
- Write dialect: `postgres`
- Still reproduces on `main` at `45158c35c`

`CAST(x AS "char")` is parsed as `CHAR`, so PostgreSQL's one-byte `"char"` becomes `bpchar` — a different type that answers the same cast with a different value.

```
input:    SELECT CAST(65 AS "char")     -- PostgreSQL: A
emitted:  SELECT CAST(65 AS CHAR)       -- PostgreSQL: 6
```

This is narrower than "quoted type names should not be resolved". Resolving them is deliberate and tested — `tests/dialects/test_postgres.py:977` asserts `1::"int"` becomes `CAST(1 AS INT)`. `"char"` is the one PostgreSQL type name where quoting changes *which type is named*, so it is the case that normalization cannot cover.

**Fully reproducible code snippet**

```python
import sqlglot

print(sqlglot.parse_one('SELECT CAST(a AS "char") FROM t', read="postgres").sql(dialect="postgres"))
# SELECT CAST(a AS CHAR) FROM t
```

The tokenizer keeps the two apart; the resolution happens in the parser:

```python
from sqlglot.dialects.postgres import Postgres

tok = Postgres().tokenizer_class()
print([(t.token_type.name, t.text) for t in tok.tokenize('"char"')])   # [('IDENTIFIER', 'char')]
print([(t.token_type.name, t.text) for t in tok.tokenize('char')])     # [('CHAR', 'char')]
```

**On PostgreSQL 17.10**

`"char"` is a one-byte internal type; unquoted `char` is `bpchar`. Neither cast raises, so the substitution is silent.

| statement | result |
|---|---|
| `SELECT CAST(65 AS "char")` | `A` |
| `SELECT CAST(65 AS CHAR)` — emitted | `6` |
| `SELECT pg_typeof(CAST(65 AS "char"))` | `"char"` |
| `SELECT pg_typeof(CAST(65 AS CHAR))` | `character` |
| `SELECT typname, typlen FROM pg_type WHERE typname IN ('char','bpchar')` | `char` → `1`, `bpchar` → `-1` |

**Why `"char"` is special rather than arbitrary**

Quoting suppresses keyword aliasing, so a quoted type name resolves against `pg_type.typname` literally and case-sensitively:

| written | result |
|---|---|
| `CAST(1 AS "char")` | `"char"` — the one-byte type |
| `CAST(1 AS "text")` | `text` |
| `CAST(1 AS "int4")` | `integer` |
| `CAST(1 AS "bpchar")` | `character` |
| `CAST(1 AS "int")` | `ERROR: type "int" does not exist` |
| `CAST(1 AS "integer")` | `ERROR: type "integer" does not exist` |
| `CAST(65 AS "CHAR")` | `ERROR: type "CHAR" does not exist` |

`int` and `integer` are grammar keywords aliasing `int4`; neither is a `typname`, so their quoted spellings do not resolve. Only names actually in `pg_type` work — and `char` is one, denoting the one-byte type rather than `bpchar`.

**Where it happens**

`Parser._parse_types` (`sqlglot/parser.py:6489`) re-tokenizes the identifier's *name*, which has already had its quotes stripped, and matches the result against `TYPE_TOKENS`:

```python
identifier = allow_identifiers and self._parse_id_var(any_token=False, tokens=(TokenType.VAR,))
if isinstance(identifier, exp.Identifier):
    try:
        tokens = self.dialect.tokenize(identifier.name)   # "char" -> char -> TokenType.CHAR
    except TokenError:
        tokens = None

    if tokens and (type_token := tokens[0].token_type) in self.TYPE_TOKENS:
        ...
    elif self.dialect.SUPPORTS_USER_DEFINED_TYPES:
        this = self._parse_user_defined_type(identifier)
```

`identifier.args["quoted"]` is available and not consulted, so a quoted name takes the same path as an unquoted one. For every type name but `"char"` that is the intended normalization.

**A possible fix**

Disabling the normalization wholesale breaks `test_postgres.py::test_postgres`, `test_redshift.py::test_cast` and `test_clickhouse.py::test_clickhouse`, which assert it. A dialect-declared exception list keeps those and fixes this one:

```python
# sqlglot/parser.py, on Parser
QUOTED_TYPES_DISTINCT_FROM_KEYWORD: t.ClassVar[set] = set()

# in _parse_types
if (
    identifier.name not in self.QUOTED_TYPES_DISTINCT_FROM_KEYWORD
    or not identifier.args.get("quoted")
) and tokens and (type_token := tokens[0].token_type) in self.TYPE_TOKENS:
    ...

# sqlglot/parsers/postgres.py, on PostgresParser
QUOTED_TYPES_DISTINCT_FROM_KEYWORD: t.ClassVar[set] = {"char"}
```

The quoted name then falls through to `_parse_user_defined_type`, which already round-trips it verbatim. On `main` at `45158c35c` this preserves `CAST(1 AS "char")`, still normalizes `CAST(1 AS "int")` to `CAST(1 AS INT)`, leaves unquoted spellings and other dialects unchanged, and `tests/test_parser.py` and `tests/dialects/` pass — 843 tests, 11545 subtests — with one pre-existing environment failure (`TestDialect::test_lazy_load`, which shells out to a `python` executable) that fails identically without the change.

**Official Documentation**

- PostgreSQL [Special Character Types](https://www.postgresql.org/docs/current/datatype-character.html) — `"char"` is one byte; `character(n)`/`bpchar` is blank-padded.
- PostgreSQL [Identifiers and Key Words](https://www.postgresql.org/docs/current/sql-syntax-lexical.html#SQL-SYNTAX-IDENTIFIERS) — a quoted identifier is never a key word.
