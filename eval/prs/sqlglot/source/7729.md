## Issue #7727: `lineage()` does not trace UNPIVOT value/name columns to their source columns (returns a phantom column on the input relation)

**Before you file an issue**
- Read dialect: `snowflake` — `lineage(..., dialect="snowflake")` (`parse_one(sql, read="snowflake")`)
- Write dialect: n/a — this is a `lineage()` issue; the AST round-trips fine via `.sql(dialect="snowflake")`
- Reproduced on **main** (`32ed149`, 2026-06-10) and on the latest release **30.10.0**

**Fully reproducible code snippet**

```python
import sqlglot
from sqlglot import exp
from sqlglot.lineage import lineage

sql = """
WITH src AS (
  SELECT id, jan, feb FROM sales
)
SELECT id, metric_name, score
FROM src UNPIVOT (score FOR metric_name IN (jan, feb))
"""
schema = {"sales": {"id": "int", "jan": "int", "feb": "int"}}

l = lineage("score", sql, schema=schema, dialect="snowflake")
print([n.name for n in l.walk()
       if isinstance(n.expression, exp.Table) and not n.downstream])
```

Output (30.10.0 and main):
```
['SRC.SCORE']
```

- **Actual:** the value column `score` resolves to `SRC.SCORE` — a column that does not exist on `src`/`sales`. The trace stops there.
- **Expected:** lineage of `score` should reach `sales.jan` and `sales.feb` (the columns listed in `IN (jan, feb)`), since the unpivot value column is derived from them. (`metric_name` likewise should relate to the unpivoted column identifiers.)

Reproduces with a base table directly as well as via a CTE (shown above).
