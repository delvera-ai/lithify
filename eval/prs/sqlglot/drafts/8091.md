In sqlglot (clickhouse dialect): Parse MODIFY COLUMN as AlterColumn.

## Issue #8019: ClickHouse MODIFY COLUMN falls back to Command instead of Alter

**Before you file an issue**
- read dialect: `clickhouse`
- write dialect: `clickhouse`
- Confirmed the issue still exists on current `main` (ea95f80).

**Fully reproducible code snippet**
```python
import sqlglot

for sql in [
    "ALTER TABLE t MODIFY COLUMN c Int64",
    "ALTER TABLE t MODIFY COLUMN c Int64 DEFAULT 0",
    "ALTER TABLE t ALTER COLUMN c TYPE Int64",
]:
    ast = sqlglot.parse_one(sql, read="clickhouse")
    print(type(ast).__name__, "->", ast.sql(dialect="clickhouse"))
```

Actual:
```
Command -> ALTER TABLE t MODIFY COLUMN c Int64
Command -> ALTER TABLE t MODIFY COLUMN c Int64 DEFAULT 0
Alter -> ALTER TABLE t ALTER COLUMN c TYPE Int64
```

`MODIFY COLUMN` also logs the unsupported-syntax fallback warning. `ALTER COLUMN ... TYPE` already parses as a structured `Alter`.

Expected:
`MODIFY COLUMN` should parse as a structured `Alter` as well (not `Command`). That is the usual ClickHouse form for type/default/codec changes:

Related: #7793 / #7968 made ClickHouse type changes generate valid `ALTER COLUMN ... TYPE`. The native `MODIFY COLUMN` parse path still falls back to `Command`.

**Official Documentation**

ClickHouse treats `MODIFY COLUMN` and `ALTER COLUMN` as equivalent. `MODIFY COLUMN` was falling back to `Command` because the ClickHouse `MODIFY` alter parser only handled `MODIFY SQL SECURITY ...`.

This maps `MODIFY` through the alter-column parser (same idea as Snowflake), returns `AlterColumn`, and canonicalizes generation to `ALTER COLUMN ... TYPE`. `IF EXISTS` is parsed on `AlterColumn` and emitted for ClickHouse. Forms the base parser cannot consume (for example `REMOVE`) still fall back to `Command`.
