In sqlglot (optimizer dialect): Memoize UNNEST/EXPLODE column-type resolution.

## Issue #7821: (bigquery) Exponential recursion when resolving UNNESTs in CTEs

Reproduced on main, 30.12.0, and 30.8.0 under bigquery (but looking at it, Spark too, except they call it `LATERAL VIEW EXPLODE`).

You know you did a good job on perf when this is the kind of edge case issue that gets filed... :) 

If the same CTE is reachable through several paths in the query, its subtree gets re-walked once per path. That makes qualify exponential in the depth of the CTE graph, for a single `UNNEST`. 

This shows up on generated SQL where several CTEs join back to a shared upstream CTE . One query in our project spends ~4s in qualify with ~3.8M calls into this function for one `UNNEST`. Which, granted, is a heck of a situation for sqlglot to find itself in, and this sql is pretty degenerate. But, here we are. 

In full disclosure, I used Claude Code to diagnose and patch this issue.

## Repro

The query builds up a per-order list of `(key, value)` attribute structs across a chain of CTEs. `orders` is the base table. `order_attrs0` starts the list with one struct. Each `order_attrs{i}` appends another struct and joins back to `orders`, so every layer reaches the shared `orders` CTE through its own path. The list is built with array functions, so its element type isn't known statically. The last CTE unnests the list to drop entries with a null value, and that unnest is what makes qualify trace the element type back through the graph. The `depth` loop only varies how many CTEs are in the chain.

```python
from sqlglot import parse_one
from sqlglot.optimizer.qualify import qualify
from sqlglot.schema import MappingSchema
import sqlglot.optimizer.resolver as resolver

SCHEMA = {"orders": {"id": "INT64"}}

def build_query(depth):
    ctes = [
        "order_attrs0 AS (SELECT id, [STRUCT('color' AS key, 'red' AS value)] AS attrs FROM orders)",
    ]
    prev = "order_attrs0"
    for i in range(depth):
        ctes.append(
            f"order_attrs{i+1} AS (SELECT a.id AS id, "
            f"array_concat(a.attrs, [STRUCT('size' AS key, 'large' AS value)]) AS attrs "
            f"FROM order_attrs{i} AS a JOIN orders AS o ON a.id = o.id)"
        )
        prev = f"order_attrs{i+1}"
    ctes.append(
        f"non_null_attrs AS (SELECT ARRAY(SELECT x FROM UNNEST(attrs) AS x WHERE NOT x.value IS NULL) AS attrs FROM {prev})"
    )
    return "WITH " + ", ".join(ctes) + " SELECT * FROM non_null_attrs"

calls = {"n": 0}
orig = resolver.Resolver._get_column_type_from_scope
resolver.Resolver._get_column_type_from_scope = lambda self, *a, **k: (calls.update(n=calls["n"]+1), orig(self, *a, **k))[1]

for depth in range(0, 13):
    calls["n"] = 0
    schema = MappingSchema(SCHEMA, dialect="bigquery", normalize=True)
    qualify(parse_one(build_query(depth), dialect="bigquery"), schema=schema, dialect="bigquery")
    print(f"depth={depth:>2}  calls={calls['n']:,}")
```

Output: the call count multiplies by ~2.6 per added CTE.

```
depth= 4  calls=110
depth= 6  calls=754
depth= 8  calls=5,168
depth=10  calls=35,422
depth=12  calls=242,786
```

(Code by Claude, reviewed by me)

`Resolver._get_column_type_from_scope` resolves the element type of an unnested/exploded column by recursing over the sources of each scope. It had no memoization, so when the same CTE is reachable through several paths of the scope graph, its subtree was re-walked once per path. Qualifying a query whose CTEs reconverge on a shared upstream CTE was therefore exponential in the depth of the graph, for a single UNNEST/EXPLODE. On a real query this reached ~3.8M calls (~4s) into the trace.

The scope and schema are immutable during qualification, so the type of a column under a given source depends only on `(source, column name)`. Cache the result on that key so each source is walked once, which makes the trace roughly linear in the size of the scope graph. Qualified output is unchanged.

Verified on BigQuery `UNNEST(col)` and Claude tells me it's also reached by Spark/Hive `LATERAL VIEW EXPLODE(col)` (this part I did _not_ verify).

Closes #7821
