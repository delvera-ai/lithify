In sqlglot (optimizer dialect): Raise OptimizeError instead of corrupting the scope graph in _traverse_union.

## Issue #8268: `_traverse_union` corrupts the scope graph when a set-operation operand isn't a Query, causing infinite recursion in `qualify()` (reproducible with valid SQL: VALUES on redshift/mysql/bigquery)

**Before you file an issue**
- Read dialect: none required for the first repro; `redshift` / `mysql` / `bigquery` (second repro, explicit below)
- Write dialect: n/a (crashes before generating output)
- Reproduces on current `main` (`bac1a897b`, 2026-08-25, `v30.17.0-72-gbac1a897b`)

**Summary**

- On pure Python this raises `RecursionError: maximum recursion depth exceeded`.
- On the compiled `sqlglot[c]` build, by the same mechanism reported in #7732, the same unbounded recursion is expected to run in mypyc-compiled frames that don't reliably honor Python's recursion check and crash the process (`SIGSEGV`) instead of raising. I did not reproduce that half myself (no `sqlglot[c]` build in my environment) — flagging it as expected-but-unverified, not confirmed.

This is **not limited to malformed SQL**. A lenient parse of truncated/malformed input can produce a non-Query operand, but so can ordinary, valid SQL on three dialects, via how they parse a bare `VALUES (...)`.

**Fully reproducible code snippets**

1) Malformed/truncated SQL (a parse fragment leaving a bare `Column` where a `Query` was expected):

```python
import sqlglot
from sqlglot.optimizer.qualify import qualify

qualify(sqlglot.parse_one("a UNION SELECT 1"))
# RecursionError: maximum recursion depth exceeded
```

2) Valid SQL — `VALUES (1) UNION ALL SELECT 1` is the exact example already used in `_traverse_union`'s own source comment ("Access the args directly instead of the left/right properties, because set operation operands aren't guaranteed to be Query nodes, e.g. in VALUES (1) UNION ALL SELECT 1"). Most dialects parse a bare `VALUES (...)` into a synthetic `Select`, which works fine. Three dialects instead parse it as `exp.Anonymous`, which hits this bug:

```python
import sqlglot
from sqlglot.optimizer.qualify import qualify

for dialect in ("redshift", "mysql", "bigquery"):
    qualify(sqlglot.parse_one("VALUES (1) UNION ALL SELECT 1", dialect=dialect), dialect=dialect)
    # RecursionError: maximum recursion depth exceeded
```

```python
def _traverse_union(scope: Scope) -> Iterator[Scope]:
    ...
    while expression_stack:
        ...
        for scope in _traverse_scope(new_scope):
            yield scope

        if prev_scope:
            union_scope_stack.pop()
            union_scope.union_scopes = [prev_scope, scope]
            ...
```

`scope` here is both the loop variable **and** the function's own parameter (`def _traverse_union(scope: Scope) -> Iterator[Scope]:`). If `_traverse_scope(new_scope)` yields nothing (the "Cannot traverse scope" warning path), the `for` loop runs zero iterations, and `scope` is left bound to whatever it held *before* the loop — on the first operand processed, that's the union's own outer scope, since nothing has reassigned it yet.

That makes `prev_scope = scope` (the `else` branch, taken on the first operand) bind `prev_scope` to the union's *own* scope rather than a real operand scope. When the second (valid) operand is then processed, `union_scope.union_scopes = [prev_scope, scope]` runs with `union_scope` being that same outer scope, so this line becomes self-referential — confirmed directly:

```python
>>> from sqlglot.optimizer.scope import traverse_scope
>>> root = traverse_scope(sqlglot.parse_one("a UNION SELECT 1"))[-1]
>>> root.union_scopes[0] is root
True
```

```python
if self._external_columns is None:
    if isinstance(self.expression, exp.SetOperation):
        left, right = self.union_scopes
        self._external_columns = left.external_columns + right.external_columns  # assigned AFTER both calls return
```

so `self._external_columns` stays `None` throughout the descent, and the `left is self` cycle recurses without ever reaching the memo guard.

**Related issues**

This is the same downstream mechanism (self-referential `union_scopes` -> unbounded `external_columns` recursion) as #8195, reached through a different malformed-operand shape. I confirmed this directly by hand-constructing #8195's exact `Alias`-wrapped-`Subquery` operand tree and running it through `traverse_scope`/`external_columns` on current `main`: it hits the identical warning (`Cannot traverse scope ... with type 'Alias'`), the identical self-reference (`union_scopes[0] is root`), and the identical `RecursionError`. #8195 was closed by a parser-level fix (a570cf8a) that stops BigQuery from mis-parsing `FULL` as an alias in that one specific construct — which prevents that particular malformed tree from being built, but doesn't touch `_traverse_union` itself, so the general failure mode is still reachable through any other route to a non-Query operand, including the two above.

I have a fix ready: give the loop its own variable, and raise `OptimizeError` immediately if `_traverse_scope` yields nothing for an operand instead of proceeding with a corrupted graph. `_traverse_ctes` in the same file already handles the equivalent situation correctly (initializes `child_scope: Scope | None = None` before its loop and checks `if child_scope:` after) — a good existing reference for the pattern. Fixes #8268.

`_traverse_union`'s per-operand loop shares its variable name (`scope`) with the function's own parameter. When `_traverse_scope()` yields nothing for an operand — which happens for any set-operation operand that isn't a `Select`/`SetOperation`/`Subquery`/`Table`/`UDTF`/`DDL`/`DML` (e.g. `VALUES (1)` on redshift/mysql/bigquery, which parses to `exp.Anonymous`, or a stray `Column` left by malformed SQL) — the loop runs zero iterations and `scope` stays bound to whatever it held before the loop. On the first operand that's the union's own outer scope, so `prev_scope` ends up pointing at the union scope itself, and processing the next operand then makes `union_scopes` self-referential (confirmed: `union_scopes[0] is union_scope`). `Scope.external_columns` recurses through `union_scopes` and only memoizes after the recursive call returns, so the cycle recurses unboundedly — `RecursionError` on pure Python, and (unverified here, no `sqlglot[c]` build available) expected `SIGSEGV` on the compiled build by the same mechanism as #7732.

This is a behavior change: previously this case silently produced a corrupted `Scope` graph; after this fix it raises a clean `OptimizeError` at the point the graph would have become corrupted, same as `_traverse_ctes` already does for the equivalent case in this file (it initializes its own loop variable to `None` and checks it after the loop — this fix follows that existing pattern).
