## Issue #8211: Postgres/DuckDB: JSON operator's right operand is not parenthesised by the generator, so output re-parses to a different tree

The generator never parenthesises the right operand of a JSON operator, so a tree whose operand binds looser than the operator is emitted as SQL that re-parses to a different tree.

Still reproduces on `main` at `a5804178a` (import reports `30.17.1.dev2`).

[#8035](), fixed by [#8063]() in v30.16.0, was the parser half of this precedence mismatch. This is the generator half: the parser now builds the tree PostgreSQL means, and the generator still prints it ambiguously.

**Read/write dialects:** `read="postgres"` → `dialect="postgres"` (and `duckdb` → `duckdb`).

## Reproduction

```python
import sqlglot

sql = "SELECT json_extract(a, 'x' || 'y') FROM t"
tree = sqlglot.parse_one(sql, read="postgres")
out = tree.sql(dialect="postgres")
print(out)
print(tree == sqlglot.parse_one(out, read="postgres"))
```

```
SELECT a -> 'x' || 'y' FROM t
False
```

Expected: SQL that re-parses to the same tree, e.g. `SELECT a -> ('x' || 'y') FROM t`.
Actual: `SELECT a -> 'x' || 'y' FROM t`, which means `(a -> 'x') || 'y'`.

It is not an artefact of the function spelling — constructing the node directly reproduces it, so any code that builds a `JSONExtract` and generates SQL is affected:

```python
from sqlglot import exp

tree = exp.select(
    exp.JSONExtract(
        this=exp.column("a"),
        expression=exp.DPipe(this=exp.Literal.string("x"), expression=exp.Literal.string("y")),
    )
).from_("t")
print(tree.sql(dialect="postgres"))
```

```
SELECT a -> 'x' || 'y' FROM t
```

## Which operands are affected

Comparing the whole tree across `parse → generate → parse`, postgres:

| operand | emitted | round-trips |
|---|---|---|
| `'x' \|\| 'y'` | `a -> 'x' \|\| 'y'` | **no** |
| `b ->> 'k'` | `a -> b ->> 'k'` | **no** |
| `b -> 'k'` | `a -> b -> 'k'` | **no** |
| `n BETWEEN 1 AND 2` | `a -> n BETWEEN 1 AND 2` | **no** |
| `n IN (1, 2)` | `a -> n IN (1, 2)` | **no** |
| `x = y` | `a -> x = y` | **no** |
| `x AND y` | `a -> x AND y` | **no** |
| `1 + 2` | `a -> 1 + 2` | yes |
| `upper('a')` | `a -> UPPER('a')` | yes |
| `CASE WHEN x THEN 'a' END` | `a -> CASE WHEN x THEN 'a' END` | yes |
| `CAST(x AS TEXT)` | `a -> CAST(x AS TEXT)` | yes |
| `k.key` | `a -> k.key` | yes |

This tracks PostgreSQL's precedence table: operands binding tighter than the "any other operator" tier are safe; operands in that tier (`||`, the JSON operators themselves) or looser (comparison, `BETWEEN`, `IN`, `AND`) need parentheses and do not get them.

`#>` / `#>>` (`exp.JSONBExtract`) behave identically — `SELECT a #> 'x' || 'y' FROM t`.

DuckDB shares the generator helper and is affected the same way. SQLite renders the function form, whose arguments cannot regroup, so it is unaffected.

```python
for d in ["postgres", "duckdb", "sqlite"]:
    t = sqlglot.parse_one("SELECT json_extract(a, 'x' || 'y') FROM t", read=d)
    print(d, "|", t.sql(dialect=d))
```

```
postgres | SELECT a -> 'x' || 'y' FROM t
duckdb   | SELECT a -> 'x' || 'y' FROM t
sqlite   | SELECT JSON_EXTRACT(a, 'x' || 'y') FROM t
```

## PostgreSQL 17

`->` and `||` are both in the "any other operator" tier and are left associative, so the unparenthesised form groups as `(jsonb -> 'x') || 'y'`.

| statement | PostgreSQL 17 |
|---|---|
| `'{"xy":1}'::jsonb -> ('x' \|\| 'y')` — what the tree means | `1` |
| `'{"xy":1}'::jsonb -> 'x' \|\| 'y'` — what SQLGlot emits | `ERROR: invalid input syntax for type json` |

The failure is loud only when the regrouped expression happens to be invalid. When it is valid the statement runs and returns a different value. For `SELECT json_extract(a, 'x' || '"y"') FROM t` SQLGlot emits `SELECT a -> 'x' || '"y"' FROM t`, and against the document `{"x":"a","xy":"b"}`:

| | PostgreSQL 17 |
|---|---|
| `-> ('x' \|\| '"y"')` — what the tree means | `NULL` |
| `-> 'x' \|\| '"y"'` — what SQLGlot emits | `["a", "y"]` |

## Where it happens

```python
def arrow_json_extract_sql(self: Generator, expression: JSON_EXTRACT_TYPE) -> str:
    this = expression.this
    if self.JSON_TYPE_REQUIRED_FOR_EXTRACTION and isinstance(this, exp.Literal) and this.is_string:
        this.replace(exp.cast(this, exp.DType.JSON))

    return self.binary(expression, "->" if isinstance(expression, exp.JSONExtract) else "->>")
```

## Suggested direction

Parenthesise the operand when it binds looser than, or level with, the JSON operator. Since #8063 made the parser follow PostgreSQL's tiers, the generator needs the matching rule for `parse → generate → parse` to be stable. Wrapping only when required leaves existing output unchanged for the common literal, column, cast and function-call operands.

*Investigated with LLM assistance. The reproductions above were run against `main` at `a5804178a` and against PostgreSQL 17 live.*

Fixes #8211.

PostgreSQL and DuckDB JSON arrow operators can change meaning when a compound right operand is emitted without parentheses. Parenthesize binary expressions, predicates, and `NOT` operands in the AST before using the existing binary generator.

This intentionally allows harmless extra parentheses for tighter binary expressions such as `a -> (1 + 2)`, avoiding a dialect-specific operator precedence list.

Tested with the full PostgreSQL and DuckDB dialect suites and the shared dialect tests.
