In sqlglot (postgres dialect): Re-escape apostrophes in Unicode string generation.

## Issue #8110: PostgreSQL Unicode string generation does not re-escape apostrophes

﻿## Bug description

SQLGlot parses a PostgreSQL Unicode escape string containing an escaped apostrophe, but the PostgreSQL generator can emit the decoded apostrophe without doubling it again. The generated SQL is then invalid or no longer represents the same AST.

This is a generated-SQL correctness defect. The reproduction uses only a benign literal and does not execute SQL or claim a security boundary.

## Environment

- SQLGlot: upstream `main@5258f24934a0f68cb42c6698db6e4992eedeb1c9`
- Python: CPython 3.12.10 on Windows
- Surface: PostgreSQL parse -> generate -> reparse

## Reproduction

```python
from sqlglot import parse_one

expression = parse_one("SELECT U&'can''t'", read="postgres")
generated = expression.sql(dialect="postgres")
print(generated)
parse_one(generated, read="postgres")
```

At the affected base, the output is:

```text
SELECT U&'can't'
```

Reparsing the generated output raises `TokenError` because the apostrophe terminates the Unicode string early. The expected output keeps the escaped delimiter, for example `SELECT U&'can''t'`, and reparses to the same expression.

## Expected behavior

The generator should re-escape apostrophes after Unicode escape substitution so that generated PostgreSQL remains valid and preserves the parsed expression.

## Negative controls

- A Unicode string without an apostrophe round-trips normally.
- The ordinary bitwise expression `SELECT u & 5 FROM t` remains a bitwise expression.
- The local validation fix reparses the apostrophe case to an equal AST and preserves backslash and custom `UESCAPE` controls.

## Local verification

- Local fix commit: `322423a0c7e2f7b6682d5442dd57b2ad5fabcb77`.
- Focused PostgreSQL test, PostgreSQL module (29 tests), relevant PostgreSQL/Presto/Oracle/generator suite (82 tests), and no-`UNICODE_START` control (26 tests) passed locally.
- Full repository CI was not run in the local worker; please run the normal project checks.

PostgreSQL U&'...' literals decode doubled apostrophes into the AST, but the generator emitted the decoded form without doubling delimiters again, producing invalid SQL such as U&'can't'. Escape string content with escape_backslash=False so Unicode escapes remain intact.
