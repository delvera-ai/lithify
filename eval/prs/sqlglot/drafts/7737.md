In sqlglot (optimizer dialect): Infinite recursion in the resolver.

## Issue #7732: Infinite recursion (RecursionError / native SIGSEGV with `sqlglot[c]`) when qualifying a `LATERAL FLATTEN`/`UNNEST` of an unqualified column over a table missing from the schema

## Summary
`sqlglot.optimizer.qualify` (and therefore `optimize`) enters **unbounded recursion** in the column `Resolver` when it tries to type a `LATERAL FLATTEN` / `UNNEST` of an **unqualified** column whose **base table is absent from the provided schema**, while a schema is otherwise present.

- On the **pure-Python** build this surfaces as `RecursionError`.
- On the **compiled `sqlglot[c]` build** the same recursion runs in mypyc-native frames that don't honor Python's recursion limit, so it overflows the C stack into an **uncatchable `SIGSEGV`** that kills the whole process. No `try/except` can recover it.

This is a **regression introduced in `30.7.0`** and still reproduces on the latest release (`30.10.0`).

## Minimal reproduction

```python
import sqlglot
from sqlglot.optimizer.qualify import qualify
from sqlglot.optimizer import optimize

# `items` is unqualified; its base table `my_db.raw.events` is NOT in the schema,
# but a schema is otherwise present.
sql = "SELECT f.value AS v FROM my_db.raw.events, LATERAL FLATTEN(items) AS f"
schema = {"my_db": {"other": {"some_view": {"v": "VARIANT"}}}}

# (a) via qualify
qualify(sqlglot.parse_one(sql, dialect="snowflake"), dialect="snowflake", schema=schema)

# (b) via optimize (qualify runs as the first rule)
optimize(sqlglot.parse_one(sql, dialect="snowflake"), dialect="snowflake", schema=schema)

# both -> pure Python: RecursionError: maximum recursion depth exceeded
#      -> sqlglot[c]:  Fatal Python error: Segmentation fault  (exit 139)
```

Removing the `schema` (or qualifying the column as `events.items`, or adding
`my_db.raw.events` to the schema) avoids it — see the trigger matrix below.

This is ordinary, idiomatic usage: a public entry point, no special options, and
a **partial schema** (the queried table simply isn't in the catalog you passed),
which is a normal and supported scenario. No `allow_partial_qualification`,
`identify`, or custom `rules` are needed to trigger it.

### Compiled (`sqlglot[c]`) — faulthandler output

```
Fatal Python error: Segmentation fault

Current thread (most recent call first):
  ...
```

(The Python stack is shallow because the deep recursion happens inside
mypyc-compiled frames, which are invisible to faulthandler; the trivial
`Dialect.__hash__` is just the call that finally tips the exhausted stack.)

### Pure Python — the repeating cycle

Running the same input on the pure-Python build with a lowered recursion limit

```
Resolver.get_source_columns            #   (lateral/unnest source)
 -> Resolver._get_unnest_column_type   #   column is unqualified, so disambiguate it
   -> Resolver.get_table
     -> Resolver._get_table_name_from_sources
       -> Resolver._get_all_source_columns
         -> Resolver.get_source_columns #   re-enters for the same lateral source  -> ∞
```

### What changed in 30.7.0

The recursive helper itself (`_get_unnest_column_type` building a parent
`Resolver` and calling `get_table` for an unqualified unnested column) already
existed in 30.6.0 — but it was only reached for BigQuery-style `UNNEST`
(`UNNEST_COLUMN_ONLY` + `exp.Unnest`), and it did not form an infinite cycle in
any version ≤ 30.6.0 that I could trigger.

30.7.0 extended `get_source_columns` to treat **`exp.Lateral`** as a column
source: `exp.Lateral` was added to the `(exp.Values, exp.Unnest, ...)` tuple and
a new branch was added —

```python
elif isinstance(source_expr, exp.Lateral) and isinstance(source_expr.this, exp.Explode):
    explode_col = source_expr.this.this
    if isinstance(explode_col, exp.Column) and source.parent:
        col_type = self._get_unnest_column_type(explode_col, source.parent)
```

This routes `LATERAL FLATTEN` into the recursive `_get_unnest_column_type` →
`get_table` disambiguation, which re-enters `get_source_columns` for the **same**
lateral source. With no re-entrancy guard, that is the infinite loop. Before
30.7.0, `exp.Lateral` never entered this branch, so the cycle was never formed.

## Trigger matrix (confirmed)

| Flattened column | Schema state | Result |
| --- | --- | --- |
| **unqualified** (`items`) | non-empty, base table **not** in it | **RecursionError / SIGSEGV** |
| qualified (`events.items`) | same | OK |
| unqualified | base table **is** in the schema | OK |
| unqualified | **no** schema at all | OK |

## Version bisect

| sqlglot | Result |
| --- | --- |
| ≤ 30.6.0 | OK |
| **30.7.0** | **regression — recursion** |
| 30.8.0 | recursion |
| 30.9.0 | recursion |
| 30.10.0 (latest) | recursion |

## Suggested fix

Break the re-entrant cycle in `Resolver`. Either:

- in `_get_unnest_column_type`, when disambiguating the unqualified column via
  `get_table`, **exclude the lateral/unnest source currently being resolved** —
  the type of the unnest *input* column cannot legitimately be derived from the
  unnest's own *output* columns; or
- add a re-entrancy guard to `_get_all_source_columns` / `get_source_columns`
  (e.g. mark a source as in-progress before computing it and return early /
  treat it as having no statically known columns on re-entry).

Because the compiled build turns this into an uncatchable native crash rather
than a `RecursionError`, a guard here is important even beyond correctness.

## Environment

- sqlglot 30.7.0 – 30.10.0 (regression introduced in 30.7.0; OK ≤ 30.6.0)
- Reproduced with both the pure-Python build (`RecursionError`) and the compiled
  `sqlglot[c]` build (`SIGSEGV`, exit 139) on Linux/amd64, Python 3.11
- Dialect: `snowflake` (any dialect that parses `LATERAL FLATTEN` / `UNNEST` of a
  column should behave the same)

Closes #7732
