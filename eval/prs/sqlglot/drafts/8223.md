Fixes #8222.

`_parse_drop` reads a single table, so the comma in `DROP TABLE t1, t2` is never consumed and the statement fails with `Invalid expression / Unexpected token` in every dialect, not only MySQL:

```python
>>> sqlglot.parse_one("DROP TABLE t1, t2", read="mysql")
ParseError: Invalid expression / Unexpected token. Line 1, Col: 14.
```

The list form is documented in the three engines that spell it out:

- MySQL — [`DROP TABLE tbl_name [, tbl_name] ...`](https://dev.mysql.com/doc/refman/8.4/en/drop-table.html)
- SQL Server — [`DROP TABLE [ schema_name . ] table_name [ ,...n ]`](https://learn.microsoft.com/en-us/sql/t-sql/statements/drop-table-transact-sql)

## Approach

The extra tables go into a new `tables` arg, following the existing `Delete.tables` convention for MySQL's multiple-table syntax. `this` keeps holding the first table, so dialect overrides that reach for it — `TSQL.drop_sql` calls `expression.this.set("catalog", None)` — are unaffected, and `drop_sql` leaves `this` untouched when `tables` is empty, so every existing single-table output is byte-for-byte identical.

The list is only parsed for `kind == "TABLE"`. `ALTER` parses its actions with `_parse_csv`, so consuming the comma for other kinds would swallow the next action and break `ALTER TABLE t DROP COLUMN a, DROP COLUMN b`, which is already covered in `identity.sql`.

Other kinds that PostgreSQL also allows a list for (`VIEW`, `INDEX`, `SEQUENCE`) are left out deliberately — `VIEW` in particular would need the `TSQL.drop_sql` override above to handle more than one node. Happy to add them here or in a follow-up if you'd prefer.
