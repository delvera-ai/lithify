- [20261023-134509-bug-humanize-naturalsize-does-no](20261023-134509-bug-humanize-naturalsize-does-no/EXPERIENCE.md) — **when** A bug-fix task in this repo where a humanize formatting function picks a branch or threshold from a converted copy of its input (e.g. `float(value)` compared against exact int powers in `filesize.naturalsize` or `number.intword`/`metric`), and the input arrives as several types (int, float, numeric str, Decimal, bool). **then** In the module's `skills/<module>-units` skill (template: `skills/humanize-filesize-units`), keep an INVARIANTS section that covers three things. First, the input contract ("whatever `float()` accepts", listing the types callers really pass). Second, which comparisons are exact and which are lossy (`float(10**24) < 10**24`). Third, one verified trap for a broad conversion, such as `Decimal(repr(Decimal))` raising, or NaN comparisons raising. Then direct that a fix adds a narrow `isinstance` branch only where precision is lost and leaves every other type on the existing path. Also require boundary rows for each mode (decimal, `binary=True`, `gnu=True`), not just the reported one.
- [20261023-133822-extend-humanize-naturalsize-to-s](20261023-133822-extend-humanize-naturalsize-to-s/EXPERIENCE.md) — **when** A task in this repo adds entries to an ordered lookup table that drives a formatting function, such as size suffixes in `filesize.py` or the prefix string in `number.metric`. Adding a unit moves the overflow cutoff and the boundaries that existing parametrize rows and docstring examples were written against. **then** Add a `skills/<module>-units` skill for that module (`skills/humanize-filesize-units` is the template). It should name the single table and its parallel entries, and say that new entries are appended rather than changing the loop. It should list each place that must stay in step: the table, the docstring `pycon` examples (checked with an explicit `--doctest-modules` run), `README.md`, and the one parametrize table. Most importantly, it should ask for new rows per mode at the exact boundary, a value just inside it, and a value past the new top unit, computed by running the code before writing expectations. Don't spend harness edits on the edited-existing-tests gate for such tasks: the task makes those edits unavoidable. Reporting rules in `system.md` left that result unchanged.
