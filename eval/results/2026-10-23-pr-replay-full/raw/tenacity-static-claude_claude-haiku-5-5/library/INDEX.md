# lithify improvement library

Each entry: what situation a lesson applies to, and the harness operation that helped.
Read an entry's EXPERIENCE.md and harness/ before reusing a component.

- [20261024-220928-bug-retrying-enabled-false-fn-an](20261024-220928-bug-retrying-enabled-false-fn-an/EXPERIENCE.md) — **when** A tenacity bug or fix about one option or surface (e.g. `enabled`, `statistics`, `reraise`) whose facts already sit in `skills/tenacity-change-contract`, but inside a section whose heading names something else (a "new keyword" or entry-point list). The fix also adds code next to an existing loop whose typing can't be checked here (mypy strict with `warn_unused_ignores`, mypy unavailable). **then** In `skills/tenacity-change-contract`, give the surface its own `## N.` heading that names it ("The `enabled` switch — which entry points honour it"), and leave a one-line pointer at the old location. Agents choose sections from `grep -n '^## '` and skip headings that don't name their subject. Under that heading, state the exact code shape to copy from the neighbouring loop, including its existing `# type: ignore[code]`. A generic "prefer a shape needing no ignore" hint in `scripts/check_changed.py` pushed the agent to `t.cast`, which is foreign to this codebase.
- [20261024-220150-bug-setting-the-module-global-te](20261024-220150-bug-setting-the-module-global-te/EXPERIENCE.md) — **when** A tenacity fix where the code next to the edit has a comment explaining a typing constraint (mypy strict, `warn_unreachable`/`redundant-expr`, an optional import kept "in a plain bool") that pytest gates cannot check and mypy cannot run to confirm. - [20261024-214815-three-regressions-that-only-appe](20261024-214815-three-regressions-that-only-appe/EXPERIENCE.md) — **when** A tenacity task restores behaviour that a recent typing/strictness commit removed or narrowed (git history shows a #677/#679/#682-style commit with a release note). The fix extends an operator or guard that the commit deliberately left rejecting some inputs, so a broad "everything else" branch would quietly undo the commit's stated promise. **then** In `skills/tenacity-change-contract`, put the strictness commit's stated invariant at the site the fix will touch, as an explicit branch condition with the commit and reno as source (e.g. "`__radd__`: combine only when `callable(other)`; a non-zero number still returns `NotImplemented`"). Wherever the skill says "widen the annotation", say in the same place that an existing test's now-unused `# type: ignore` stays as it is and gets reported, not removed.
- [20261024-152742-bug-retry-if-exception-cause-typ](20261024-152742-bug-retry-if-exception-cause-typ/EXPERIENCE.md) — **when** A tenacity task reports a hang (infinite loop, 100% CPU, a strategy or chain walk that never returns), so the regression test can't fail by assertion on unfixed code. Each red run lasts at least `--timeout` seconds, may outlast the shell tool's foreground limit, and on this host can stretch far past its limit when the machine is descheduled. **then** Define what red means for a hang in the always-on `system.md` step 1: `run_tests.py --timeout 20 <one node id>` returning `exit=124` with `HUNG IN:` naming the new test. In the same paragraph, set the shell call's timeout above S, forbid `perl alarm`/raw-pytest/background fallbacks, and allow one fallback: wait for the completion notice without killing the run. Have `scripts/run_tests.py` print wall and CPU seconds, so a stall where wall time is much larger than CPU time is read as host descheduling, not a broken bound. Keep red-test recipes for hangs out of `skills/tenacity-change-contract`: in these rollouts the skill was read only after the fix was in, and a recipe there (a thread-based test) arrived too late and led to a revert of the fix.
- [20261023-214407-bug-retry-if-exception-message-m](20261023-214407-bug-retry-if-exception-message-m/EXPERIENCE.md) — **when** A tenacity task in which the agent has to consult the large `tenacity-change-contract` skill (about 30 KB, many `## N.` sections) but needs only a few sections, typically §2 (reno note) and the docs/tests sections for a small user-visible fix. Reword the existing "where skills live" bullet instead of adding a new always-on line.

- [20261023-210731-bug-retrying-enabled-false-is-ig](20261023-210731-bug-retrying-enabled-false-is-ig/EXPERIENCE.md) — **when** A tenacity bug report says one usage form (the iterator `for`/`async for`, a direct `Retrying(...)(fn)` call, tornado) should "match" or "behave like" another path that already handles the option (usually the `@retry`/`wraps` decorator). - [20261023-204745-api-cleanup-every-other-exponent](20261023-204745-api-cleanup-every-other-exponent/EXPERIENCE.md) — **when** A tenacity task renames, replaces or deprecates a constructor argument of a public strategy or class: "add X with the same meaning, deprecate Y, Y must still work but warn, passing both raises". - [20261023-201420-improvement-composing-several-re](20261023-201420-improvement-composing-several-re/EXPERIENCE.md) — **when** The change in this tenacity repo has to work for both the sync and the async variant of an operator or strategy (`retry_base` vs `async_retry_base`). Python's reflected-operator dispatch sends mixed sync/async operands to the async class's `__ror__`/`__rand__`, so a fix that only handles same-family operands passes the pure-sync and pure-async tests but leaves the mixed case behaving differently. **then** In `skills/tenacity-change-contract/SKILL.md`, give each operator the change touches a written rule stating which side of a mixed sync/async expression handles it (`sync_x | async_y` → `async_retry_base.__ror__`) and which direction of absorption is safe: an async container may take sync members, a sync container must never take async ones. If the mixed case still behaves differently, it must be reported as unmet, not as a "choice to redirect".
