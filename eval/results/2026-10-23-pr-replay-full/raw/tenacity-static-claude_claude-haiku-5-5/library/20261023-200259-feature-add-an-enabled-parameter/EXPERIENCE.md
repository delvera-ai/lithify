# 20261023-200259-feature-add-an-enabled-parameter

**Task:** Feature: add an `enabled` parameter (default `True`) to `Retrying`, `AsyncRetrying` and the `@retry` decorator. With `enabled=False` the decorated function is called directly, exactly once, with no retry logic, and any exception it raises propagates unchanged. This is useful during development and testing.

## Transferable lesson

- **cue:** A tenacity task adds a run-time option or behaviour switch to `Retrying`/`AsyncRetrying`/`@retry`, where the request is worded around the decorated call but users can also start a run through `for attempt in Retrying(...)`, `async for`, or `TornadoRetrying`.
- **lesson:** In `skills/tenacity-change-contract` (SKILL.md), name every run entry point explicitly (`Retrying.__call__`, `BaseRetrying.__iter__`, `AsyncRetrying.__call__`, `AsyncRetrying.__aiter__`, `TornadoRetrying.__call__`) and require each to be handled or listed as left out. Saying in general that `BaseRetrying`/`_begin_iter` owns the loop is not enough: agents that had only that sentence still guarded just the `__call__` methods.
- **evidence:** First `skills/tenacity-change-contract` row (§1c entry-point bullet). It was present in dom-1 and comp-1, which both branched in `_begin_iter` and covered iteration. It was absent in base-1 and inv-1, which both left iteration retrying, even though the base skill already mentioned `_begin_iter`.
- **confidence:** medium. The result held in 2 of 2 rollouts with the bullet and 2 of 2 without, and dom-1's trajectory ties the decision to the skill text (l.182 → l.213). But there is one rollout per candidate, all four passed gates, and only one task type was observed.
