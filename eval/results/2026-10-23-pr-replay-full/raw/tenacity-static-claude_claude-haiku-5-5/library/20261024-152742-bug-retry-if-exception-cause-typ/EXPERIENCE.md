# 20261024-152742-bug-retry-if-exception-cause-typ

**Task:** Bug: `retry_if_exception_cause_type` hangs forever (100% CPU, stop conditions never run) when an exception's `__cause__` chain is cyclic, e.g. `raise e from e`, or two exceptions whose causes point at each other. Walking the cause chain must terminate on cycles while still finding a matching cause type anywhere in a non-cyclic chain.

## Transferable lesson

- **cue:** A tenacity task reports a hang (infinite loop, 100% CPU, a strategy or chain walk that never returns), so the regression test can't fail by assertion on unfixed code. Each red run lasts at least `--timeout` seconds, may outlast the shell tool's foreground limit, and on this host can stretch far past its limit when the machine is descheduled.
- **lesson:** Define what red means for a hang in the always-on `system.md` step 1: `run_tests.py --timeout 20 <one node id>` returning `exit=124` with `HUNG IN:` naming the new test. In the same paragraph, set the shell call's timeout above S, forbid `perl alarm`/raw-pytest/background fallbacks, and allow one fallback: wait for the completion notice without killing the run. Have `scripts/run_tests.py` print wall and CPU seconds, so a stall where wall time is much larger than CPU time is read as host descheduling, not a broken bound. Keep red-test recipes for hangs out of `skills/tenacity-change-contract`: in these rollouts the skill was read only after the fix was in, and a recipe there (a thread-based test) arrived too late and led to a revert of the fix.
- **evidence:** rows `system.md` and `scripts/run_tests.py` (inv-1, comp-1 compared with base-1: no kills or `perl alarm`, per-test `exit=124` red evidence, correct reading of the "wall 905s/783s" stalls, about 1780 s against 4299 s). Row `skills/tenacity-change-contract` (skill loaded after the fix in dom-1 and comp-1; dom-1's thread recipe led to the `git show HEAD` revert).
- **confidence:** low. Two rollouts support it, and `system.md` and `run_tests.py` never changed separately, so which one did the work is unknown. Host descheduling happened in every run, which adds a lot of noise. The run-time difference is one sample per arm. The applied deliverable came from the base harness, so the gain is in process only, not output quality.
