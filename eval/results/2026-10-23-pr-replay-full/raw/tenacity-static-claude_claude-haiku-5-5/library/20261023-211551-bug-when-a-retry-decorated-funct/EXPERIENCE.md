# 20261023-211551-bug-when-a-retry-decorated-funct

**Task:** Bug: when a `@retry`-decorated function is further wrapped by another decorator that uses `functools.wraps` (for example a timing decorator), `func.statistics` on the outer wrapper is an empty `{}` instead of the real runtime statistics. The statistics must stay visible through such wrappers, for sync and async functions (the outer wrapper's `statistics` should be the same object as the inner one's).

## Transferable lesson

- **cue:** A tenacity fix changes how per-call or per-thread runtime state is exposed or shared, for example `fn.statistics` on a decorated function, through `functools.wraps`, `copy()`, `retry_with` or `threading.local`. The obvious fix (one shared object) quietly breaks an invariant that only a code comment or docstring mentions.
- **lesson:** In `skills/tenacity-change-contract`, give that surface its own section. List its invariants explicitly, with where each comes from (a code comment, the property docstring, an issue number). Require the final message and reno note to keep each one or name it as changed. A one-line mention such as "statistics is per-thread" is not enough.
- **evidence:** The §1a1 row of skills/tenacity-change-contract. base-1 and inv-1, without the list, shipped a shared dict or a non-dict view and left the tradeoff open. dom-1 and comp-1, with it, kept per-call dicts that write through to a shared one and checked each listed invariant.
- **confidence:** medium. The contrast holds in 2 rollouts against 2 and matches what selection preferred. But only dom-1 isolates the skill edit, there is one rollout per arm, and the existing live-statistics tests also pushed dom-1 and comp-1 away from their first snapshot attempt.
