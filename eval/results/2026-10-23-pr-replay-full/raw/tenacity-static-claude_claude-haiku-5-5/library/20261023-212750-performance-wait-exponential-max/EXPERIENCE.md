# 20261023-212750-performance-wait-exponential-max

**Task:** Performance: `wait_exponential(max=...)` still computes `exp_base ** attempt_number` on every retry even after the result has reached `max`, so long-running polling gets more and more expensive (the integer grows without bound). Once the exponential would exceed `max`, return `max` without performing the power operation. (Stated requirement: the power must not be computed for attempts beyond the cap.) Results must otherwise be unchanged.

## Transferable lesson

- **cue:** A tenacity task frames the change as cost-only, such as a performance fix or a rewrite of a strategy's internals, and says results must stay unchanged. The agent then has to decide whether the change is "user-visible" enough to need the repository's ship-alongside files.
- **lesson:** In `skills/tenacity-change-contract`, name results-preserving performance and refactor fixes in the `description` trigger. In §2, state that "results unchanged" is not an exemption from the reno note: a user-reported slowdown ships a `fixes:` note. Any other skill that handles results-preserving changes, such as `behavior-preserving-change`, should end with a pointer to load tenacity-change-contract. Without this, the agent rules itself out of the contract on the "not user-visible" reasoning.
- **evidence:** The skills/tenacity-change-contract row. base-1 and inv-1, without the edit, both skipped the note and gave the "results identical, not user-visible" reason. dom-1 and comp-1, with it, both shipped a `fixes:` note. In comp-1 the pointer in skills/behavior-preserving-change is what loaded the contract.
- **confidence:** medium. The contrast is consistent across all four rollouts, with the rationale quoted verbatim on both sides. But each harness has only one rollout, and the edit arrived together with other changes (§1b4 in dom-1, three components in comp-1).
