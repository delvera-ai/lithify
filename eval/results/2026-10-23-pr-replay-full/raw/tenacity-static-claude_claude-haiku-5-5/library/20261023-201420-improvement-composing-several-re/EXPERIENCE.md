# 20261023-201420-improvement-composing-several-re

**Task:** Improvement: composing several retry conditions with `|` or `&` currently nests containers, e.g. `a | b | c` becomes `retry_any(retry_any(a, b), c)`. Chained operators should flatten into a single container instead: `a | b | c` must produce one `retry_any` whose `retries` holds `a`, `b` and `c`, and likewise `&` must produce one `retry_all`; the same for the async retry strategies. ## Transferable lesson

- **cue:** The change in this tenacity repo has to work for both the sync and the async variant of an operator or strategy (`retry_base` vs `async_retry_base`). Python's reflected-operator dispatch sends mixed sync/async operands to the async class's `__ror__`/`__rand__`, so a fix that only handles same-family operands passes the pure-sync and pure-async tests but leaves the mixed case behaving differently.
- **lesson:** In `skills/tenacity-change-contract/SKILL.md`, give each operator the change touches a written rule stating which side of a mixed sync/async expression handles it (`sync_x | async_y` → `async_retry_base.__ror__`) and which direction of absorption is safe: an async container may take sync members, a sync container must never take async ones. Also list the operand mixes the tests must cover (all sync, all async, sync→async, async→sync, plain callable on each side). If the mixed case still behaves differently, it must be reported as unmet, not as a "choice to redirect".
- **evidence:** skills/tenacity-change-contract row. base-1 had no such rule and left mixed chains nested, labelled as a choice. dom-1 (SKILL.md the only change), inv-1 and comp-1 all handled the mixed case and cited the skill at the decision point.
- **confidence:** medium. The contrast holds in 3 of 3 candidate rollouts against 1 base rollout, and dom-1 isolates the component. But there is one rollout per harness, and base-1 had already spotted the gap itself, so the rule may have tipped a decision rather than revealed it.
