# 20261023-210731-bug-retrying-enabled-false-is-ig

**Task:** Bug: `Retrying(enabled=False)` is ignored when used with the iterator pattern (`for attempt in retrying: with attempt: ...` and `async for attempt in AsyncRetrying(enabled=False)`): the full retry loop runs (several attempts) and a `RetryError` is raised. With `enabled=False` the body should run exactly once and any exception should propagate unchanged, matching the decorator path.

## Transferable lesson

- **cue:** A tenacity bug report says one usage form (the iterator `for`/`async for`, a direct `Retrying(...)(fn)` call, tornado) should "match" or "behave like" another path that already handles the option (usually the `@retry`/`wraps` decorator). The existing path does that by short-circuiting before the shared loop machinery (`begin()`, `before`/`after` hooks, statistics), so a fix can stop the retries and pass the gate while still running that machinery.
- **lesson:** In `skills/tenacity-change-contract`, write down exactly what the reference path does and skips, as a verified fact with a grep to recheck it. For example: "`enabled` is checked in `wraps` before `copy()`, so there is no `begin()`, no `before`, and statistics stay `{}`". Also state whether a branch in shared `_begin_iter`/`iter()` would leak into `__call__`, and require the final message to say which of the skipped steps the new path still runs. Name the docs section that describes the reference path so its sentence gets widened too.
- **evidence:** skills/tenacity-change-contract row (dom-1 isolates it: skipped `begin()` and edited the docs; base-1 and inv-1 ran `begin`/`before`, edited no docs, and base-1 still claimed it matched the decorator path)
- **confidence:** medium. The contrast is consistent: 2 of 2 rollouts with the edit against 0 of 2 without, and dom-1 changed only this component. But there is one rollout per harness, all four passed gates, and the evidence is selection's judgment of fidelity rather than a test failure.
