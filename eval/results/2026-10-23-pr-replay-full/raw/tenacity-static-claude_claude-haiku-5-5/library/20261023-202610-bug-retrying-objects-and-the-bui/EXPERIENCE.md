# 20261023-202610-bug-retrying-objects-and-the-bui

**Task:** Bug: `Retrying` objects and the built-in retry strategies cannot be pickled, so `@retry`-decorated functions cannot be used with `multiprocessing` (e.g. `Pool.map`). Make `Retrying` instances (including ones that have already been used and have statistics) and the retry strategy classes picklable with the standard `pickle` module, restoring an equivalent working object.

## Transferable lesson

- **cue:** A tenacity task asks for a capability (pickling, copying, sending across processes or threads) that depends on hidden per-object state, such as `BaseRetrying._local`, lazily built `statistics`/`iter_state`, or lambdas and closures stored by strategy `__init__`s. The scenario the user names (for example `Pool.map(decorated_fn)`) may not exercise the object that actually fails, so a run without the facts either reads whole modules to find the state or tests the wrong path.
- **lesson:** In `skills/tenacity-change-contract/SKILL.md`, add a section on object state. Name each piece of hidden state and say where it is created. Name the one base class whose hooks the subclasses inherit. Name which object actually crosses the boundary, so tests target `fn.retry` or a used `Retrying` directly. Include a grep that lists offending strategy classes, the out-of-scope unpicklables, and the side effects to report (e.g. `copy.copy` now going through the hooks). Explicitly separate state the task requires to survive (e.g. `statistics` of a used `Retrying`) from scratch state (`iter_state.actions`). Do not group them under "per-run state", because a carrier that read that wording dropped the required state. Keep this in the on-demand skill, not in `system.md`.
- **evidence:** skills/tenacity-change-contract row (dom-1 and comp-1 both ran the skill's grep instead of reading the whole module, tested a used `Retrying` across a spawn Pool, and reported the skill's out-of-scope list; comp-1's dropped statistics echoes the skill's "per-run" / "empty statistics" wording); contrast with base-1's full-file read and its unverified "already worked" claim.
- **confidence:** medium. Two rollouts show the same behaviour change, and dom-1 isolates the skill as the only changed component. But there is one rollout per label, the gate (pytest only) passed everywhere, and the warning about separating state rests on a single rollout (comp-1).
