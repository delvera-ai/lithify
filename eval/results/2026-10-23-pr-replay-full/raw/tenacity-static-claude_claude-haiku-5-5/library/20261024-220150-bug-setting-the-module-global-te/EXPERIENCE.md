# 20261024-220150-bug-setting-the-module-global-te

**Task:** Bug: setting the module global `tenacity.tornado = None` (the usual way a test suite exercises the non-tornado path without uninstalling tornado) makes any subsequent `@tenacity.retry` decoration raise `AttributeError: 'NoneType' object has no attribute 'gen'`. Whether tornado is available must be read from the live module global at decoration time, so decorating works after the global is set to `None`.

## Transferable lesson

- **cue:** A tenacity fix where the code next to the edit has a comment explaining a typing constraint (mypy strict, `warn_unreachable`/`redundant-expr`, an optional import kept "in a plain bool") that pytest gates cannot check and mypy cannot run to confirm. The obvious one-line fix quietly brings back the pattern the comment warns against.
- **lesson:** In `system.md`, require loading `tenacity-change-contract` (headings plus the sections for the area) before the first edit under `tenacity/`, and require that any fix satisfy the reason given in a comment beside the changed code, or that the final message say why it does not. When the skill documents such a constraint, also name the concrete compliant shape (as comp-1's §1e does with the `_has_tornado() -> bool` helper). A bare prohibition led to an odd workaround (`globals().get`).
- **evidence:** system.md row (base-1 l.48-51 read the comment and ignored it, versus inv-1 l.60 quoting it and choosing the helper with an unchanged skill); skills/tenacity-change-contract row (dom-1's bare prohibition gave `globals().get`, comp-1's named shape gave the helper); scripts/check_changed.py row (the mechanical check never fired, so it is not the lever).
- **confidence:** low. Each contrast comes from one rollout per harness. The system.md edit bundles two rules. All four rollouts passed the same gates, and mypy never ran, so the "better" fix is judged only on fidelity to the comment's reason and the code, not on a verified type check.
