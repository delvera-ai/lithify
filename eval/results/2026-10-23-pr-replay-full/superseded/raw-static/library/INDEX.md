# lithify improvement library

Each entry: what situation a lesson applies to, and the harness operation that helped.
Read an entry's EXPERIENCE.md and harness/ before reusing a component.

- [20261023-164433-feature-add-an-enabled-parameter](20261023-164433-feature-add-an-enabled-parameter/EXPERIENCE.md) — **when** A tenacity feature adds a new configuration knob to `Retrying`/`AsyncRetrying`/`@retry`, or mirrors an attribute that an earlier commit already threaded through the class family. The work is spread over several sites (constructor, `copy()`, subclass re-declarations, decorator overloads, `__repr__`), and agents reliably find the call paths but drop the passive sites. **then** In `skills/tenacity-change-contract`, keep a per-site checklist taken from the precedent commit (the `name`/#597 sites, including `__repr__`), triggered from the skill's description. Phrase the execution-path part as a list of where the knob could matter, not as an order to change every loop: the same "reach every execution path" sentence led one rollout to add iterator-path machinery the task never asked for.
- [20261023-163902-feature-attemptmanager-the-objec](20261023-163902-feature-attemptmanager-the-objec/EXPERIENCE.md) — **when** A tenacity feature task describes only the runtime behaviour (here, "`async with attempt:` should work like `with attempt:`") and does not mention docs or examples. A harness edit proposes adding another file that features "must" touch to the contract skill, citing that past feature commits touched it (e.g. `doc/source/index.rst`). **then** In `skills/tenacity-change-contract/SKILL.md`, keep the required artifact list at code + reno note + regression test. Do not add `doc/source/index.rst` (or any similar convention mined from commit history) as a required file for features. If it is mentioned at all, make it conditional ("only if the task asks for docs or changes a documented example"), and leave it out of the "Confirm they agree" required-diff list and the skill `description`. Without such a rule, rollouts deliver the smaller change that was preferred. With it, they reliably add out-of-scope doc blocks they cannot verify.
- [20261023-161759-regression-since-8-4-2-composing](20261023-161759-regression-since-8-4-2-composing/EXPERIENCE.md) — **when** A tenacity regression task lists several variants of the bug (operand orders, `|` and `&`, sync and async strategies, decorator vs `Retrying`) and asks that all of them work. Some variants may already work on HEAD because they take a different code path, for example `async_retry_base` overrides of the operators that `retry_base` delegates. **then** In `skills/tenacity-change-contract/SKILL.md`, give the agent steps to follow, not only facts about the code paths. Before any edit, run one snippet on unmodified HEAD that tries each named variant in its own try/except and prints which ones raise. Then require that every variant named in the task is exercised by a test, and that each test function contains at least one case that fails on HEAD (so fails_on_base still passes). Don't tell the agent to build tests only from the cases that fail, because that drops the working orders and async coverage from the tests and the release note.
- [20261023-161138-bug-the-delay-since-first-attemp](20261023-161138-bug-the-delay-since-first-attemp/EXPERIENCE.md) — **when** A tenacity regression test has to catch an exception, such as `KeyError` or `AttributeError`, raised by user code reading retry state while an attempt is running. The tempting test does the read inside `with attempt:` or inside the retried function, where tenacity's own machinery catches the exception and retries. **then** In `skills/tenacity-change-contract/SKILL.md`, don't just describe the swallowing mechanism; prescribe the test placement. Read the value outside `with attempt:` (at the top of the `for attempt in ...` body) or in a `before=` hook, so the bug's own exception reaches pytest. Make the DONE step "check that the fails_on_base output shows the bug's exception type, not an `AssertionError` from a count". Also remind that the sync `for attempt` loop needs `contextlib.suppress(RetryError)`, because fails_on_base exit 0 does not prove the test passes on the fix.
- [20261023-160401-bug-tenacity-after-log-crashes-w](20261023-160401-bug-tenacity-after-log-crashes-w/EXPERIENCE.md) — **when** The tenacity-change-contract skill asks the agent to verify something, such as "test fails on the old code", but gives no command for it. The only obvious way to do it is a state-changing git round-trip (stash/apply/drop, or hand-reverting the fix) on the working tree that holds the deliverable. **then** Ship the check as a deterministic, read-only script under `skills/tenacity-change-contract/scripts/` (temp copy of HEAD plus the working-tree tests, with clear exit codes and a "report not verified on exit 2" rule). Add an explicit invocation line in `skills/tenacity-change-contract/SKILL.md`'s DONE checklist, where the requirement is stated. Don't leave the agent with prose that just says "verify it".
- [20261023-155945-bug-tenacity-utils-find-ordinal](20261023-155945-bug-tenacity-utils-find-ordinal/EXPERIENCE.md) — **when** The task fixes or changes user-visible behaviour in tenacity (log or error text, defaults, API), and the task text only asks for the code fix. The harness has nothing that tells the agent about the repo's ship-with-fix artifacts (reno notes in `releasenotes/notes/`). **then** Keep the on-demand skill `skills/tenacity-change-contract` and its one-line pointer in `memory.md`. The skill spells out the reno note (file name pattern, `fixes:`/`features:` YAML, no edits to `changelog.rst`) and the test-module map. Without it, rollouts deliver a correct code-only fix and leave out the release note. Add new repo-convention facts to this skill rather than to always-on `system.md`.
