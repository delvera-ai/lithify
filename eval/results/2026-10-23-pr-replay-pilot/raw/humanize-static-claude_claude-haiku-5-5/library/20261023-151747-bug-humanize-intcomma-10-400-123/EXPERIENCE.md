# 20261023-151747-bug-humanize-intcomma-10-400-123

**Task:** Bug: `humanize.intcomma(10**400 + 123)` raises `OverflowError` with the default `ndigits=None`. Python can format such integers with thousands separators directly, so very large integers (positive and negative) should be grouped correctly with every digit preserved. Behaviour for numeric strings and for explicit `ndigits` is unchanged.

## Transferable lesson

- **cue:** A humanize formatter bug where the correct output is long or tedious to write out (huge ints, many digit groups, long repeated strings), and the agent adds cases to the function's existing `@pytest.mark.parametrize` list. Agents then tend to compute `expected` with the very expression the implementation uses (e.g. `f"{x:,}"` inside `intcomma`), so the test passes for any output.
- **lesson:** In the module's `skills/<module>-output` test item (here `skills/humanize-number-output` item 3), say that `expected` must be a string literal, as in every existing case, and must never be built with the format call the function under test uses, because such a test passes whatever the function returns. Allow building a long literal from repeated pieces, and give that pattern generically (`"1" + ",000" * k` for `10**(3*k)`), never as this task's actual expected value.
- **evidence:** skills/humanize-number-output row. base-1 wrote `f"{10**400 + 123:,}"` as expected. dom-1 and comp-1 both wrote hand-built literals. comp-1 had only the generic example, so the rule did the work, not a leaked answer.
- **confidence:** medium. The contrast held in both candidate rollouts, and in comp-1 without the task-specific example. But each harness ran only once, base-1 is a single sample, and the rule arrived bundled with other sub-edits in the same file. The bundled edits (description, guard rewrite) touch the source fix and skill discovery, not test construction, so they are unlikely to explain it.
