# 20261023-142958-bug-humanize-naturalday-and-huma

**Task:** Bug: `humanize.naturalday()` and `humanize.naturaldate()` give the wrong answer for timezone-aware datetimes. They compare against the system's local date, so when the date in the datetime's own timezone differs from the system date the result is off by a day. Example: if it is currently `2023-10-15 23:00 UTC`, a datetime 7 hours later expressed in AEDT (`+11:00`) is still "today" in AEDT, but humanize reports "tomorrow". For tz-aware datetimes, "today" must be determined in that datetime's time

## Transferable lesson

- **cue:** A humanize task where two public functions share logic and one calls the other (here `naturaldate` → `naturalday`), and a harness skill states a rule that keeps the two consistent.
- **lesson:** In the `skills/<name>` for that module, phrase a cross-function rule as a check to run on the finished diff ("for each new test input, `naturaldate(x)` and `naturalday(x)` give the same today/tomorrow/yesterday label"). Do not phrase it as a design requirement ("both must use the same notion of today / must not disagree"). The requirement wording led the agent to restructure the functions so they could not disagree, which is an unrequested refactor. The check wording keeps the existing call structure and still catches the near-miss through a test.
- **evidence:** The skills/humanize-time-module row. dom-1 changed only this skill, cited "so the two functions cannot disagree" when introducing `_natural_day`, and was ranked last by selection for that refactor. comp-1's softer wording did not prevent the stripped-date mistake, but it kept the call structure. The adopted base-1 had no skill.
- **confidence:** low. A single rollout (dom-1) stands behind the link between the wording and the refactor, and comp-1's wording differs from dom-1's in more than this one rule. The link is a direct quote in the trajectory, though, not something inferred.
