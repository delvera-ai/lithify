# lithify improvement library

Each entry: what situation a lesson applies to, and the harness operation that helped.
Read an entry's EXPERIENCE.md and harness/ before reusing a component.

- [20261023-151747-bug-humanize-intcomma-10-400-123](20261023-151747-bug-humanize-intcomma-10-400-123/EXPERIENCE.md) — **when** A humanize formatter bug where the correct output is long or tedious to write out (huge ints, many digit groups, long repeated strings), and the agent adds cases to the function's existing `@pytest.mark.parametrize` list. Agents then tend to compute `expected` with the very expression the implementation uses (e.g. `f"{x:,}"` inside `intcomma`), so the test passes for any output. **then** In the module's `skills/<module>-output` test item (here `skills/humanize-number-output` item 3), say that `expected` must be a string literal, as in every existing case, and must never be built with the format call the function under test uses, because such a test passes whatever the function returns. Allow building a long literal from repeated pieces, and give that pattern generically (`"1" + ",000" * k` for `10**(3*k)`), never as this task's actual expected value.
- [20261023-150818-bug-humanize-naturaldelta-docume](20261023-150818-bug-humanize-naturaldelta-docume/EXPERIENCE.md) — **when** A humanize bug fix where the task names one public function, but sibling functions in the same module (e.g. `naturaltime`, `precisedelta` beside `naturaldelta`) take the same bad input through a different code path that the fix won't reach. Without a written description of how the functions call each other, the agent fixes the named function and never runs the siblings. **then** In the module's `skills/<module>-output` skill (e.g. `skills/humanize-time-output`), state as verified facts which public function calls which, and which path converts the input (e.g. "`naturaltime` reaches `naturaldelta` only after `_date_and_delta` has built a timedelta, so a guard in `naturaldelta` doesn't cover it"). Add a check for the finished diff: "fix only the function the task names; run each sibling on the new inputs and report those that still fail in the final message". Keep the fix itself out of the skill, and put repo-wide conventions (imports, parametrize style) in `memory.md` rather than in the skill.
- [20261023-150254-bug-humanize-fractional-produces](20261023-150254-bug-humanize-fractional-produces/EXPERIENCE.md) — **when** A humanize fix or edit near the end of the task, where a lint or type tool that `pyproject.toml` or tox configures (ruff, mypy) is not installed in the project venv, and the harness names that tool or its rules without saying it is missing. **then** In always-on `tool_guidance.md`, give one bullet to each configured-but-missing checker. Name it, give the exact failure (`No module named …`), say "don't run or install it", give a fallback that reads `[tool.ruff]` in `pyproject.toml` against the changed lines, and require the final message to say the check was not run. In any `skills/<name>` that lists that tool's rules (e.g. mypy `strict`, `RUF046`), point back to that bullet rather than naming the tool alone, because naming a tool without saying it is missing triggers a probe.
- [20261023-145531-bug-humanize-naturalsize-can-sho](20261023-145531-bug-humanize-naturalsize-can-sho/EXPERIENCE.md) — **when** A humanize bug fix where the agent must show the reported output on the unmodified code and prove each new parametrize case changes output, and the harness has no ready-made old-vs-new tool. In that situation agents fall back on swapping `git show HEAD:<file>` over the working tree and copying the fix back in one shell chain. **then** Keep `scripts/compare_outputs.py` in the harness (HEAD via `git archive` to a temp dir, a separate subprocess per side, a `C changed` summary line, exit 2 on setup failure). Point to it from always-on `tool_guidance.md` with the exact call form and an explicit ban on copying HEAD files over the tree, and say it is meant for both steps: before editing, to reproduce the bug (expect 0 changed, read the `old:` lines), and after editing, to confirm the new cases. The pointer alone was enough to get it adopted; no `system.md` wording was needed. Do not expect it to catch wrong test expectations; only the suite run does that.
- [20261023-144514-bug-humanize-metric-can-output-a](20261023-144514-bug-humanize-metric-can-output-a/EXPERIENCE.md) — **when** A humanize bug fix that changes what a formatter returns, where the agent has to show the reported output on the unmodified code and confirm each new parametrize case changes (or sweep many inputs for unintended changes). This is the point where agents start rebuilding HEAD by hand: loading two copies of the package in one process, `git show` into /tmp, or copying HEAD files over the working tree. **then** Ship the old-vs-new comparison as a harness script (`scripts/compare_outputs.py`: HEAD via `git archive` into a temp dir, each side in its own subprocess, checks the import path, ends with an `N expressions, C changed` line, exit 2 on setup failure). Point to it from `tool_guidance.md` with the "don't write your own: a shared `sys.modules` silently reports no change" warning, plus the "no `-I`" note. Don't rely on `system.md` wording alone to get this verification done correctly.
- [20261023-143921-bug-humanize-fractional-1-3-retu](20261023-143921-bug-humanize-fractional-1-3-retu/EXPERIENCE.md) — **when** A humanize bug-fix task where the reported failing inputs sit beside neighbouring inputs that already give the right (or quirky) output, such as other signs, zero, or values that round to 0, and the agent adds regression cases to an existing `@pytest.mark.parametrize` list. **then** Define "done" for a bug fix in always-on `system.md`, not in a module `skills/<name>`. Every new test case must fail on the unmodified code, and inputs that already behaved correctly go in the final message rather than in the test list. Also tell the agent to run the original code once, before editing, on every input it plans to add as a test, so it doesn't have to rebuild HEAD afterwards to check them.
- [20261023-142958-bug-humanize-naturalday-and-huma](20261023-142958-bug-humanize-naturalday-and-huma/EXPERIENCE.md) — **when** A humanize task where two public functions share logic and one calls the other (here `naturaldate` → `naturalday`), and a harness skill states a rule that keeps the two consistent. **then** In the `skills/<name>` for that module, phrase a cross-function rule as a check to run on the finished diff ("for each new test input, `naturaldate(x)` and `naturalday(x)` give the same today/tomorrow/yesterday label"). Do not phrase it as a design requirement ("both must use the same notion of today / must not disagree"). The requirement wording led the agent to restructure the functions so they could not disagree, which is an unrequested refactor. The check wording keeps the existing call structure and still catches the near-miss through a test.
- [20261023-142559-humanize-i18n-raises-a-bare-exce](20261023-142559-humanize-i18n-raises-a-bare-exce/EXPERIENCE.md) — **when** A humanize task that narrows or changes behaviour that existing tests only check loosely. For example, `pytest.raises(Exception, match=...)` still passes after the type is narrowed to a subclass, and would pass if the change were never made. So the existing suite cannot show the new behaviour, and the agent is tempted to "tighten" those assertions. **then** In the `skills/<name>` that covers the change, write the verification step as "pin the new behaviour by adding a NEW test function beside the existing one (same setup, same `match`); do not modify any pre-existing test line, even to make it stricter." Do not phrase it as "make sure some test asserts the new type". Agents satisfy that wording by rewriting the existing assertions, which counts as editing existing tests.
- [20261023-142110-regression-when-gnu-is-false-hum](20261023-142110-regression-when-gnu-is-false-hum/EXPERIENCE.md) — **when** Adding parametrized cases to a humanize test where the test body changes each case's arguments before asserting again (for example, `test_naturalsize` re-runs every case negated by prefixing `-` to non-int inputs), so a case that looks valid fails on the second assertion. **then** Put the test function's argument-transformation contract in `memory.md` as one line saying which inputs are legal there. Do not put it inside a task-specific `skills/<name>` that also encodes the fix. A future task that adds cases to that test then avoids writing a case the retest will break, without loading a skill whose solution hints can pull its tests toward inputs that were never broken.
